# Architecture

Onprest is designed to expose only agent-defined capabilities, not the database itself.

The agent prepares only the providers and sources referenced by configured capabilities at startup. DB capabilities are classified as SELECT or mutation. Mutations execute in explicit transactions. When data output is enabled, they publish native affected count only after a successful commit; omitted output publishes null data while retaining measured metrics. An optional [affected-count limit](/agent/capability-yaml#policy) is checked before commit and triggers transaction rollback if exceeded. A gateway timeout or in-flight disconnect leaves a mutation outcome unknown even when cancellation was requested.

```text
[API user / MCP client]
  |
  | REST / MCP / OpenAPI / healthz
  v
[onprest-gateway]
  ^
  | outbound connection from Agent
[onprest-agent + capability.yaml]
  |
  v
[configured on-prem source]
```

## Mental Model

1. Define a capability on the on-prem side.
2. Define its input contract, execution policy, and operation-specific output contract.
3. Start the agent inside the customer network.
4. The agent connects outbound to the gateway.
5. REST and MCP clients call only capabilities their API key can access.
6. The agent validates input, applies policy, executes the prepared capability against its approved sources, validates selected output, and returns data or independent file snapshots.

The gateway does not receive private schema knowledge, SQL, DSNs, DB credentials, or execution rules. Those stay inside the on-prem agent, where `capability.yaml` defines the only executable operations. The gateway receives only the agent-generated public capability contract needed for OpenAPI and MCP discovery.

## Design Principle

The gateway handles "who can call what." The Agent owns "what each capability means" and the execution boundary.

This separation is the core of Onprest.

- The gateway does not store SQL text.
- The gateway does not store DB host, user, or password.
- Runtime gateway requests carry the capability name, HTTP params, deadline, prepared definition hash, and caller binding.
- The agent validates HTTP params against `input`, enforces policy, and selects and validates data/files using the configured `output`; DB SELECT uses `output.items` and DML uses `output.properties`. Omitting output still executes but publishes `result.data: null`.
- OpenAPI / MCP tools are generated from the agent definition.

Even if the gateway is compromised, the attacker can learn the Agent-defined public capability contract, but the Gateway has no place to create unknown SQL, holds no DB credentials, and cannot bypass the capability contract and execution policies enforced by the Agent.

## AI / MCP Fit

This design is a natural fit for AI and MCP clients because it does not ask the cloud-facing caller or gateway to be trusted with database power. AI agents call explicit tools generated from approved capabilities, while the on-prem agent enforces the actual contract.

In practice, an AI agent receives a narrow tool such as `get_customer` or `search_orders`. It does not receive a DSN, unrestricted SQL executor, DB credentials, or raw schema access. The gateway can be compromised or misused and still cannot invent operations outside `capability.yaml`.

## OSS Deployment Boundary

The OSS core is two independent binaries.

| Component | Deployment unit | Responsibility |
|---|---|---|
| gateway | `onprest-gateway` | REST / MCP / OpenAPI / healthz / WebSocket / API key auth / capability auth |
| agent | `onprest-agent` | YAML lint / source preparation / input validation / prepared capability execution / output validation / local detail logs |

## Gateway Responsibilities

The gateway is a Go single binary and does not persist application state. It reads authentication configuration at startup and keeps runtime state, such as the public capability cache and active connections, in memory. Runtime state is rebuilt after restart.

- API key authentication
- Per-API-key capability-level authorization
- IP allow list
- trusted proxy handling
- per-source HTTP rate limiting
- REST endpoint
- MCP endpoint
- `/openapi.json`
- `/healthz`
- agent WebSocket endpoint
- stdout JSON logging
- graceful shutdown
- separate encoded JSON and multipart input limits; see [Gateway configuration](/gateway/configuration#request-body-limit)

Agent connections are limited to one live connection. Before upgrade, the gateway issues a one-time, one-minute challenge that is included in the Ed25519-signed handshake and consumed atomically. Issued challenges do not survive a gateway restart, so a complete pre-restart handshake cannot be replayed afterward. Non-loopback agent transport requires `wss://` by default. The gateway sends WebSocket ping frames and requires timely pong traffic, so a stale TCP session is closed and a replacement may connect. If another agent tries to connect while the existing session is still live, the gateway rejects it and writes a warning log.

All outbound agent messages pass through one bounded writer queue with write deadlines. Each request has independent pending state; disconnect or write failure releases affected callers immediately instead of waiting for the request timeout. Meta retrieval, including invalid metadata, is retried with bounded backoff only for the current connection generation, and disconnected metadata is not served as current state.

## Agent Responsibilities

The agent is also a Go single binary. It is deployed on the on-prem side together with `capability.yaml`.

- outbound WebSocket connection to the gateway
- Connection signing with an Ed25519 private key
- `capability.yaml` lint
- preparation of referenced providers and sources
- DB ping and SQL EXPLAIN verification for DB capabilities
- folder root validation, input ownership, atomic file saves, and independent snapshots
- input schema validation
- policy enforcement
- optional per-capability Agent rate limiting before execution admission
- execution of prepared capabilities against approved sources
- output selection and schema enforcement
- OpenAPI spec generation
- runtime detail output to the local log
- reconnect every 30 seconds
- up to `runtime.max_concurrent_requests` concurrent capability executions per connection (default 16), with an equally bounded waiting queue

Normal startup and `onprest-agent validate` share the same configuration and referenced-provider preparation. DB Ping/EXPLAIN apply only to DB capabilities; HTTP preparation sends no business request. See [HTTP executors](/agent/capability-yaml#http-executors). Validation closes those resources and exits without connecting to the Gateway or executing a capability. `onprest-agent doctor` reuses that preparation to diagnose Gateway connectivity and Agent-key authentication without changing the running connection. Normal startup alone transfers the prepared resources to the runtime Runner and connects.

`capability.yaml` is loaded at startup, then the agent runs from the in-memory definition. Restart the agent to apply changes.

File snapshots are retained in the Agent private spool. Gateway issues authenticated, expiring references from an explicit configured origin and streams downloads without persisting bodies. File input uses one REST JSON/multipart or MCP arguments call. Complete input validation and EOF precede execution; multipart streams to Agent spool with ACK backpressure. File saves target prepared writable folders. See [File Output](/api/files) for lifetime, caller separation and transfer limits.

## Capability Tunnel

A normal gateway-to-agent request carries the capability name and HTTP params with the deadline, prepared definition hash, and caller binding.

```json
{
  "type": "request",
  "id": "01J5ABCDEF1234567890ABCDEF01",
  "capability": "get_customer",
  "params": {
    "customer_id": 1
  },
  "deadline": "2026-10-03T09:00:05Z",
  "definition_hash": "64 lowercase hex characters from prepared metadata",
  "caller_binding": "opaque caller binding"
}
```

The agent checks whether the capability exists, whether params match the contract, and whether policy is satisfied before executing it. For DB capabilities, omitted or true `readonly` accepts one `SELECT`; explicit false also accepts one `INSERT`, `UPDATE`, or `DELETE`. The dialect-aware scanner rejects multiple statements and recognizes nested block comments in PostgreSQL and SQL Server. Integer JSON tokens remain exact through signed 64-bit conversion; DB values are normalized before validation against the declared `output` types and constraints. With data output enabled, SELECT publishes selected rows and DML publishes the non-negative native affected count; omitted output publishes null while preserving execution and measured metrics.

## Dedicated Gateway Model

Onprest assumes a dedicated gateway process per customer.

In this model, API keys, the agent public key, OpenAPI cache, and stdout logs are not shared across customers. Because the gateway has no persistent DB and is separated by process and environment variables, the operational unit matches the trust boundary.

## TLS and Network Edge

Network-edge infrastructure and TLS termination are environment-owned. The gateway can be exposed directly or placed behind an optional compatible reverse proxy or load balancer. See [Reverse Proxy](/gateway/reverse-proxy) when using one.

Database TLS is independent from gateway-edge TLS. PostgreSQL, MySQL, SQL Server, and Oracle support `require` and `verify-full`; PostgreSQL additionally supports `verify-ca`. The default is `disable`. `verify-full` authenticates the trust chain and configured host name, while `require` provides encryption only. Optional client certificates are supported for PostgreSQL and MySQL. Unsupported combinations and verification failures are rejected instead of silently downgraded. See [Database configuration](/agent/capability-yaml#sources-and-protected-files) and the [database-specific guides](/databases) for field-level configuration.

## Product Boundary

Managed products and dashboards are outside the OSS core. They are not dependencies of either OSS binary and their product or operating policies are not defined by this repository.
