# Security

Onprest is designed to reduce the boundary under the assumption that every component can be compromised. The gateway carries the Agent-generated public contract, but the Agent alone owns capability meaning and execution.

## Trust Model

| Boundary | Holds secrets | Holds SQL | External role |
|---|---:|---:|---|
| gateway | agent public key, API key hashes | No | routing, identity, observability, filtered public metadata |
| agent | agent private key, source credentials | Yes | capability execution |

The gateway routes capability names and params and serves the Agent-generated public contract. DB connection information, SQL text, and raw agent detail are never written to gateway HTTP responses or stdout logs. HTTP errors return a stable `code` and public `message`.

## Gateway Compromise

Even if the gateway is compromised, the Agent rejects capabilities outside `capability.yaml`. A registered code capability can choose operations from its params, so the code and its param handling are part of the execution boundary.

For mutations, grant the agent DB user only the required table-level INSERT, UPDATE, or DELETE privileges. Do not grant schema/DDL or unrestricted database privileges. `readonly` lint is a syntactic guardrail and cannot prove that a SELECT-invoked DB function has no side effect, so least privilege remains the final boundary. DML is never retried automatically after a timeout or disconnect because the transaction outcome may be unknown.

- SQL text does not exist in the gateway.
- DB credentials do not exist in the gateway.
- The OpenAPI cache contains only Agent-generated public metadata, not SQL or DB connection information.
- The agent rejects unknown capabilities.
- The agent rejects inputs outside the params contract with `VALIDATION_FAILED`.
- The agent can enforce a per-capability `policy.rate_limit` even if a compromised gateway sends requests without applying its own HTTP rate limit.
- Normal output with declared `output.items.properties` selects only those SELECT fields. `output.data: {}` without a row schema and `mode: passthrough` can publish all returned fields; the configuration author chooses that exposure. DML data output publishes a validated affected-count object and may use `max_affected_rows` to roll back mutations larger than policy. See [Output](/agent/capability-yaml#output).

The gateway knows which API key can call which capability and can serve its public contract. Capability meaning and execution remain on the Agent.

## API Key Authorization

API keys use explicit capability-level authorization.

```json
[
  {
    "name": "partner-a",
    "key_hash": "$2a$10$...",
    "capabilities": [
      "get_customer",
      "get_orders"
    ]
  },
  {
    "name": "internal",
    "key_hash": "$2a$10$...",
    "capabilities": [
      "*"
    ]
  }
]
```

- Omitted or empty capabilities mean zero permissions.
- All capabilities are allowed only when `"*"` is explicitly set.
- REST, MCP, and OpenAPI use the same API key authentication and capability authorization.

## Agent Validation Boundary

The agent is the only OSS core component that owns capability meaning.

At startup:

- It lints the YAML structure and required fields.
- It prepares only referenced providers and sources; HTTP preparation sends no business request.
- For DB capabilities, it verifies SQL with each DB's EXPLAIN mechanism.
- It stops startup if preparation fails, including a referenced DB Ping failure.

At runtime:

- It checks whether the capability is defined.
- It rejects unknown input properties by default, plus invalid types, enum violations, out-of-range values, and invalid formats.
- It applies timeout and max-bytes policy to every operation, and max rows to DB SELECT and CSV.
- After capability and params validation, it applies any capability rate limit before execution-queue or database admission. Unknown capabilities and invalid params do not consume tokens.
- DB capabilities pass parameters through prepared statements.
- It applies configured output selection and validation; field filtering depends on the declared output schema and mode. See [Output](/agent/capability-yaml#output).

## Fixed HTTP sources

HTTP capabilities keep source origins, paths, headers and credentials on the Agent. Callers supply only declared arguments; they cannot replace the destination URL or authorization headers. The Agent checks destination DNS/IP and HTTPS certificates on every hop, ignores ambient proxies, and restricts configured redirects to the same origin. Private IPs are allowed by default; loopback/link-local/multicast need explicit CIDRs. See [HTTP sources and bindings](/agent/capability-yaml#sources-and-bindings).

Review each capability's permitted method, explicit input bindings and output exposure. An HTTP request can have an irreversible business effect even if its response is lost or invalid. `effects: none` is a descriptive hint; it does not authorize an automatic retry or prove rollback. Requests are not automatically retried after failure.

## Agent Secret Leakage

If the agent private key leaks, rotate the key.

Before each WebSocket handshake, the agent obtains a one-time challenge with `POST /ws/agent/challenge`. The gateway then verifies an Ed25519 signature over this exact UTF-8 byte sequence (with LF separators and no trailing LF):

```text
onprest-agent-v2
<request path>
<RFC3339 timestamp>
<nonce>
<gateway challenge>
<Sec-WebSocket-Key>
```

The gateway validates the signature before atomically consuming both the challenge and nonce. Challenges expire after one minute, are bounded in memory, and exist only in the gateway process that issued them. A captured complete handshake therefore fails both after first use and after a gateway restart. Binding `Sec-WebSocket-Key` prevents substitution of a different handshake key; it is not, by itself, a replay store.

Use `wss://` for every non-loopback agent connection so challenges and authentication headers cannot be captured from the network. Plain `ws://` is accepted by default only for loopback development. `gateway.allow_insecure_non_loopback_ws: true` is an explicit escape hatch for an isolated development network and must not be used in production.

Concurrent connections are limited to one agent. If a fake agent tries to connect with the same key while the legitimate agent is already connected, the gateway rejects it with `CONFLICT`.

`onprest-agent doctor` uses the same one-time challenge store but a separate signature domain:

```text
onprest-agent-verify-v1\n{path}\n{RFC3339 timestamp}\n{base64url nonce}\n{gateway challenge}
```

The challenge endpoint itself requires no API key or Agent signature; it is bounded by the Gateway's IP/rate controls and the one-minute challenge lifetime. `/ws/agent/verify` requires a valid signature over the dedicated domain above, then consumes the challenge and nonce atomically. It does not open or replace a WebSocket connection. See [CLI Reference](/reference/cli#diagnose-agent-and-gateway) for the command contract.

## Product Boundary

Managed products and dashboards are outside the OSS core security boundary. Their UI, storage, administration, and operating policies are not OSS gateway or agent guarantees.

## Sensitive Detail Handling

External HTTP responses and gateway stdout never include raw detail. Public errors use safe codes, messages, observed outcomes and optional fixed reasons; see [Errors](/api/errors).

```json
{
  "request_id": "01J5ABCDEF1234567890ABCDEF01",
  "error": {
    "code": "EXECUTION_FAILED",
    "message": "database query failed",
    "outcome": "unknown"
  }
}
```

DB-specific errors and SQL execution detail stay in agent-local logs; DB credentials, Agent keys, API keys, authorization values, and submitted param values are not emitted as public diagnostics. Standalone diagnostics use protected files separate from the rotating runtime log. See [Agent Local Logs](/agent/local-logs).

Agent rate-limit rejections use a fixed public message and never include submitted params. Rejection logging is bounded; see [Agent Local Logs](/agent/local-logs).


## File output boundary

File references require the original API credential and current permission for the original capability on every retrieval. They are bound to the current definition and authenticated Agent connection, expire, and are lost on restart or reconnect. URI knowledge alone does not authorize a download. The Gateway does not enumerate retained files or fetch external resource URIs. It derives references only from the configured [file reference origin](/gateway/configuration#file-reference-origin).

The Gateway enforces caller separation; the Agent validates its retained owner and connection generation. This boundary assumes an uncompromised Gateway: the Agent does not independently authenticate an end caller's assertion made by a compromised Gateway. Folder roots and private spool permissions remain operator responsibilities. Publish completed producer files by atomic rename and avoid modifying files in place during snapshot acquisition. See [File Output](/api/files).

## Wasm code boundary

Deploy only reviewed code and validate every argument that selects a path or destination. Sandbox OFF code can read host credentials and use the Agent OS user's resources. Sandbox ON limits FS/network/environment access to explicit grants, but cannot prevent disclosure to an allowed destination or guarantee rollback of file changes and HTTP side effects. Output selection controls the API result; it cannot prevent code from sending data directly over HTTP. Keep OS permissions and grants narrow. See [Wasm executors](/agent/capability-yaml#wasm-executors).
