# Capability YAML

`capability.yaml` defines sources, accepted input, executors, policy, and published output. Normal startup, `onprest-agent validate --config PATH`, and the preparation portion of `doctor` compile and prepare the same definition. Preparation resolves protected secret/TLS files for referenced providers and sources. DB capabilities open and Ping their databases and perform driver-specific EXPLAIN; HTTP preparation sends no business request. No capability executes during preparation. Validation does not connect to the Gateway or reload a running Agent.

## Structure

This is a capability excerpt, not a complete configuration. The [Quick Start DB configuration](/quick-start) includes `schema_version`, gateway, and database sources. The [HTTP example](https://github.com/viewlegacy/onprest/tree/dev-2.0.0/examples/http) supplies a complete configuration without a database.

```yaml
capabilities:
  get_customer:
    description: Find a customer by ID.
    executor:
      type: db
      source: primary
      sql: select id, name from customers where id = :id
    input:
      properties:
        id: {type: integer, minimum: 1}
      required: [id]
    policy:
      timeout: 5s
      max_rows: 1000
      max_output_bytes: 1MB
    output:
      data: {}
      items:
        properties:
          id: {type: integer}
          name: {type: string}
  update_customer:
    executor:
      type: db
      source: primary
      sql: update customers set name = :name where id = :id
    input:
      properties:
        id: {type: integer, minimum: 1}
        name: {type: string, minLength: 1, maxLength: 200}
      required: [id, name]
    policy:
      readonly: false
      timeout: 5s
      max_affected_rows: 1
    output:
      data: {}
```

The runtime supports DB executors with PostgreSQL, MySQL, SQL Server, and Oracle, including CSV output, CSV executors reading configured folders or uploaded files, file read/write executors with file input, and HTTP executors calling fixed API sources. Wasm executors run prepared WASI command modules in isolated workers; see [Wasm executors](#wasm-executors). Each DB capability selects `executor.source` and owns its prepared database connection pool. File reads and writes select named folder sources.

Capability names match `^[a-zA-Z][a-zA-Z0-9_.-]{0,127}$`; names beginning with `onprest_` are reserved.

`schema_version: 1` is required. The compiler rejects unknown or duplicate keys, multiple YAML documents, invalid UTF-8, and contradictory settings. YAML aliases and merges are supported; direct values override merged values. Apply changes using the [capability change procedure](/operations/capability-changes).

## Top-Level Sections

| Section | Purpose |
|---|---|
| `schema_version` | Required configuration version, `1` |
| `service` | Public OpenAPI title, version and description |
| `runtime` | Execution concurrency, private spool, and persistent identity directory |
| `gateway` | Gateway WebSocket URL and Agent signing key |
| `sources.databases` | Named database connections selected by DB executors |
| `sources.folders` | Fixed folder roots selected by CSV reads and file reads/writes |
| `sources.http` | Fixed API sources selected by [HTTP executors](#http-executors) |
| `logging` | Local detail log settings; see [Agent Local Logs](/agent/local-logs#rotation) |
| `defaults` | Applicable policy defaults |
| `capabilities` | At least one named executable operation |

`runtime.max_concurrent_requests` defaults to `16`, with an equally bounded waiting queue; see the [Agent runtime model](/agent#runtime-model). Gateway URL and transport requirements are described in [Deployment](/operations/deployment#self-hosted-minimal-settings).

Normal Agent startup opens `runtime.spool_dir` (default `./spool`, relative to the configuration directory) before receiving requests. It must be a private, writable directory owned by the Agent user, dedicated to one Agent process. Unsafe permissions, links, another process's lock, or recovery failure prevent startup. `runtime.spool_total_bytes` defaults to `1GiB`; this quota covers temporary input and output snapshots, unfinished save files, and cleanup reservations. Input and output snapshots do not survive restart as usable handles. Preserve the spool directory across restarts when it contains persistent cleanup records; see [spool recovery](/operations/troubleshooting#private-spool-recovery-prevents-startup) for startup failures and safe recovery. `validate` and `doctor` do not open the running Agent's spool.

`runtime.control_limits` applies independently of capability rate limits to Agent management requests. Its fixed `read`, `write`, `cancel`, and `transfer` classes each accept `requests`, `per`, `burst`, and `max_concurrent`. The shared logical I/O budget uses `bytes_per_second` (default `8MiB`) and `burst_bytes` (default `16MiB`). `max_concurrent_transfers` defaults to `4`, with an effective concurrency cap of `8`. Refused management operations return `RATE_LIMITED` or `BUSY` and do not replace existing request state. File downloads use these fixed management limits in addition to their transfer deadline. These same management limits also bound input transfers.

## Sources and protected files

Database connection fields are under `sources.databases.<name>`. `password` and `password_file` are mutually exclusive; file bytes are not trimmed. Relative secret and TLS paths resolve from the configuration directory. Secret files must be regular, owned and protected files; symlinks and unsafe permissions fail closed. TLS uses the existing driver-specific modes and CA/client-certificate settings described in [Databases](/databases). Secret and TLS bytes are captured once during preparation and are included in the definition binding; execution does not reread those paths.

`gateway.agent_private_key` and `agent_private_key_file` are mutually exclusive. The file contains the exact canonical base64url Ed25519 private key, with no trailing newline. The key signs Agent authentication handshakes and diagnostic challenges. A protected identity key under `runtime.identity_dir` (default `./identity`, relative to the configuration directory) binds prepared definitions; keep this directory private and writable by the Agent user. Changing a source, secret, TLS material, or effective execution contract changes its definition hash. Logging and presentation changes do not.

## Input

`input` is a recursive object schema. `properties`, `required`, `items`, `additionalProperties`, `type`, `enum`, `const`, `default`, `minimum`, `maximum`, `minLength`, `maxLength`, `pattern`, and supported formats validate supplied values. `properties` and `items` imply object and array types. Unknown input properties are rejected by default. Missing properties receive their declared defaults before validation; explicit null is not a missing value. Nullable input declares a union such as `type: [string, 'null']`.

Supported string formats are `email`, `uuid`, `date`, `date-time`, and `uri`. Patterns use a common subset: literals, character classes, groups, alternation, repetition, and `^`/`$` anchors. Lookaround, backreferences, inline flags, Unicode-property/POSIX classes, and unsupported escapes are rejected at compile time. `\d` and `\w` use ASCII classes; anchor a pattern when it must match the whole value.

JSON integers remain signed int64. The API rejects duplicate JSON keys, invalid UTF-8, integer overflow, non-finite numbers, and excessive bytes, depth, or item count. The Agent applies `max_input_bytes`, `max_json_depth`, and `max_json_items` before and after default application. DB input does not accept files. SQL named parameters must refer to declared scalar input properties.

File input uses `type: file`, optional `extensions`, `mime_types`, positive `max_bytes`, and `allow_empty` (default true). Extensions are ASCII names without a leading dot, normalized to lowercase; MIME restrictions and extensions both apply. The [public file input representations](/api/files#file-input) are generated from this schema. `policy.max_input_file_bytes`, `max_total_input_file_bytes`, and `max_input_files` default to `32MiB`, `64MiB`, and `16`. A leaf's `max_bytes` can narrow the single-file policy. JSON and file bytes use separate budgets.

`runtime.input_limits` sets positive `max_pending_requests` (default 16), `max_multipart_parts` (128), and `max_recent_requests` (4096). `runtime.transfer_timeout` defaults to `60s`, at most `300s`, and bounds the full input phase without restarting for another part. `policy.timeout` bounds execution after complete validated input.

## Policy

`defaults` supplies applicable policy defaults; a capability's `policy` overrides them. Explicit policy keys that do not apply to the executor or SQL operation fail compilation.

| Setting | Default | Meaning |
|---|---|---|
| `readonly` | `true` | DB only: true permits SELECT; false also permits INSERT, UPDATE and DELETE |
| `timeout` | `5s` | One execution/output-validation budget, at most `300s`; caller cancellation/deadline can shorten it |
| `max_rows` | `100` | DB SELECT truncates at this row count; CSV returns `LIMIT_EXCEEDED` if the filtered total across all files exceeds it |
| `max_affected_rows` | unset | DB DML only: count limit; exceeding it rolls back |
| `max_input_bytes` / `max_output_bytes` | `1MB` | Input bytes / published JSON data and selected data used to generate CSV; original file bytes use the file policy limits below |
| `max_json_depth` / `max_json_items` | `32` / `100000` | Recursive structure limits |
| `rate_limit` | unset | Required `requests`, `per`, and `burst`; admission occurs before queueing |
| `expose_in_openapi` | `true` | Advertise the prepared capability in OpenAPI/MCP |

A capability inherits the complete `rate_limit` object from `defaults` when omitted, or replaces it with its own object. Each capability has an independent bucket shared by its callers, starting with `burst` tokens and replenishing at `requests` per `per`. Gateway reconnection preserves the bucket; Agent restart resets it. A token consumed at admission is not returned after a later busy response, cancellation or execution failure.

Byte sizes accept positive integer bytes or units such as `KB`/`MB`. SQL must be one SELECT, INSERT, UPDATE, or DELETE; WITH, MERGE, DDL, procedure calls, transaction control, and row-returning DML are rejected. Dialect-aware scanning handles quoted text and comments. Finite Agent concurrency and waiting queues remain bounded; saturation returns `BUSY` without execution.

## Output

`output.data: {}` opts in to JSON publication. DB SELECT and CSV declare their row schema through `output.items`; DML describes its count object with `output.properties`. An omitted output still executes and records measured metrics, but succeeds with `result.data: null` and `result.files: []`. Generic JSON output retains the selected object, array, scalar or null without adding a rows/count wrapper; see [HTTP responses](#responses-and-redirects). Publishing DB SELECT or CSV data returns `{rows: [...], count: n}` inside `result.data`; DML returns `{count: n}`, where count is native non-negative `RowsAffected()` and zero is success.

Normal output selects declared fields recursively, then validates their types and constraints. Empty `properties: {}` publishes no fields. Omitted type/properties allows JSON values; `mode: passthrough` preserves fields and still validates declared constraints. Output `nullable` defaults to true; null and required presence are separate rules. Declared DB SELECT and CSV columns are checked against column metadata even with zero rows. A DML output must retain count.

The DB adapter normalizes native driver values before output validation; output declarations never coerce strings to numbers or other types. See [Database JSON values](/databases#json-values) for decimal, binary, timestamp and NULL representations.

DML runs in one transaction. The Agent validates affected count, output selection/types/constraints and capacity before commit. Validation failure confirms rollback before reporting `rolled_back`; an unconfirmed commit or rollback reports `OUTCOME_UNKNOWN` with `unknown`. A successful commit is never executed again. Check independent database state before retrying any mutation with an unknown outcome.

## File writes

A file executor's `write` list binds existing required file positions with RFC 6901 pointers, such as `/document` or `/documents`. Direct file arrays used by a required write binding must declare `minItems: 1`. Each write chooses a prepared `source` folder with `access: write` or `read_write`, optional relative `path`, and exactly one of a fixed `name` or `name_from: input`. Destination directories must already exist. Input display names become business names only with explicit `name_from: input`.

```yaml
sources:
  folders:
    exchange: {root: ./exchange, access: read_write}
capabilities:
  save_report:
    executor:
      type: file
      write: [{input: /document, source: exchange, name: report.pdf}]
      read: {written: true}
    input:
      properties:
        document: {type: file, extensions: [pdf], mime_types: [application/pdf], max_bytes: 8MiB}
        month: {type: string}
      required: [document]
    output: {files: {}}
```

Writes validate all destination names and capacity before publication, stage privately, and publish using native no-replace operations. Existing files conflict by default. `overwrite: true` uses safe native exchange on Linux/macOS; replacing an existing target is rejected on Windows and on filesystems without the required primitive. The server rejects links, changed identities, reserved names, and unsafe destinations. A later partial publication reports an unknown outcome and does not delete completed business files. `read.written: true` returns completed writes in write/array order; `read.source` selects independently after all saves. Save-only capabilities succeed with `data: null` and `files: []`. Validation and doctor prepare definitions without writing business files or acquiring the running spool.

## CSV executors

CSV executors parse every input file, filter rows, then apply the common output definition to JSON and generated CSV. They do not require a database. See the [two-binary CSV example](https://github.com/viewlegacy/onprest/tree/dev-2.0.0/examples/csv) for a folder download and uploaded-file conversion.

```yaml
sources:
  folders:
    reports: {root: ./reports, access: read}
capabilities:
  selected_sales:
    executor:
      type: csv
      read: {source: reports, selector: {name: sales.csv}}
      csv: {columns: {amount: {type: integer}}}
      where: [{column: month, op: eq, input: /month}]
    input: {properties: {month: {type: string}}, required: [month]}
    output:
      items: {properties: {id: {type: string}, amount: {type: integer}}}
      data: {}
      files: {format: csv, filename: selected-sales.csv}
```

### Read inputs

`read` requires either a folder `source` and [selector](#file-reads-and-csv-output), or `input: /documents`. The input Pointer must identify a required file or required file array with `minItems` at least 1; every enclosing object and referenced array index must also exist. Folder selector settings cannot accompany `read.input`. With uploaded input, declare `documents` under `input.properties` as `{items: {type: file, extensions: [csv]}, minItems: 1}` and add it to `required`. The [file request forms](/api/files#file-input) apply unchanged; the CSV executor does not save uploaded originals into a business folder.

### Parsing

`executor.csv` is optional. Omitted or empty settings use `header: true`, `encoding: utf-8`, and `delimiter: comma` (`,`). A delimiter is one character other than NUL, CR, LF, double quote, or the replacement character. With a header, omitted or empty `columns` reads every column as a string. A partial map changes parsing only for named columns; other columns remain available to filters and output selection. Numeric-looking strings such as `00123` and empty strings are preserved.

Each column accepts `type` (`string`, `integer`, `number`, `boolean`; default `string`), `nullable` (default `false`), and `null_values` (default `[]`). Only exact matches in `null_values` become null, and only when `nullable: true`; a configured null with `nullable: false` fails parsing. Integers are signed decimal digits within int64; numbers are finite decimal values with optional exponent. Whitespace, hexadecimal numbers, NaN and infinity are rejected. Booleans are exactly `true` or `false`. With `header: false`, every column needs a unique, contiguous zero-based `position`. Configured columns must exist even when there are no data rows.

Supported encodings are strict `utf-8`, `shift_jis` (JIS X 0208), and `cp932` (Windows-31J, including Windows extensions). They are not aliases: for example `0x8160` becomes `〜` in Shift_JIS and `～` in CP932. Invalid or truncated bytes and unassigned characters fail parsing. A UTF-8 BOM is preserved as U+FEFF, including in the first header name; it is not silently removed. Record boundaries use LF or CRLF; CR/LF inside quoted fields are preserved. Quotes escape through doubled quotes. Duplicate or empty headers, broken quoting, and mismatched field counts fail.

### Filtering and output

`where` is an optional array of `{column, op, input}` conditions combined with AND. Operators are `eq`, `ne`, `lt`, `lte`, `gt`, `gte`, and `in`. Input Pointers must identify required values with the parsed column type; `in` requires a typed array of that same type. Nested objects and array indices must have guaranteed presence. Omitted parser columns have type `string`. Actual null arguments or null array elements fail before CSV reads; null CSV cells match no operator, including `ne`. String ordering uses UTF-8 byte order, integers retain int64 precision, and boolean ordering is `false` before `true`.

Folder files follow selector order; uploaded arrays follow input order. Every file must have the same column names and order. All rows, including filtered-out rows, must parse successfully. `max_rows` applies to the filtered total across all files, and exceeding it returns `LIMIT_EXCEEDED`. A zero-row filter succeeds with `rows: []` and `count: 0`; a folder selector with no match returns `NOT_FOUND`. Malformed CSV fails with `EXECUTION_FAILED`; an output type or declared-column mismatch fails with `OUTPUT_INVALID`. Failed parsing never publishes partial JSON or a generated-file prefix.

Parsed values pass through [common output selection and validation](#output) without string-to-number conversion. [CSV generation](#file-reads-and-csv-output) uses the same selected rows; `columns` can select and order a subset. Omit `data` for files only or `files` for JSON only. Use a file executor to return original bytes.

Publish completed folder inputs through temporary files and atomic rename. Folder raw snapshots consume the Agent's shared `runtime.spool_total_bytes` quota until parsing and output validation complete; uploaded inputs already consume that quota. Quota exhaustion returns `LIMIT_EXCEEDED`. The quota is a disk budget, not a process RSS limit. JSON structure limits apply to filtered rows before output selection; `max_output_bytes` measures published JSON and selected CSV source data, not discarded CSV columns.

## HTTP executors

HTTP executors bind validated inputs to a configured API and apply the [common output definition](#output) to its JSON or original response bytes. They require no database. The [two-binary HTTP example](https://github.com/viewlegacy/onprest/tree/dev-2.0.0/examples/http) demonstrates arguments → upstream API → selected JSON.

```yaml
sources:
  http:
    inventory:
      base_url: https://inventory.internal.example
      allowed_methods: [POST]
      credential_file: ./secrets/inventory-token
capabilities:
  get_inventory:
    executor:
      type: http
      source: inventory
      method: POST
      path: /stock
      query: {region: {value: east}}
      headers: {X-Channel: {value: onprest}}
      body: {kind: json, fields: {item: {input: /item}}}
      response: {kind: json}
    input: {properties: {item: {type: string}}, required: [item]}
    output: {properties: {item: {type: string}, available: {type: integer}}, data: {}}
```

### Sources and bindings

`sources.http.<name>` requires an HTTP(S) `base_url` and an `allowed_methods` array. `allowed_cidrs` optionally narrows destination IPs. Without CIDRs, private IPs are allowed while loopback, link-local and multicast are denied; permit these explicitly only when intended. Every connection checks DNS/IP and HTTPS certificates. Ambient proxy settings are ignored. Optional fixed `headers` are string values. `credential` or protected `credential_file` supplies an exact UTF-8 Bearer token; the two are mutually exclusive, empty/CRLF values are rejected, and a token must not include the `Bearer ` prefix. Preparation captures the secret once without sending a business request.

`method`, `source`, and the absolute `path` are fixed configuration. The absolute path determines the destination path, replacing any path in `base_url`. Put query parameters in `query`, not in the path. Each query/header/body field binds either `{input: /pointer}` or `{value: fixedJSON}`, never both. Pointers use RFC 6901, including `''` for the entire input object, and must reference declared schema positions. Values use validated inputs after defaults. There is no string interpolation or automatic forwarding of all params. JSON bindings cannot contain input files.

`query` accepts non-null scalars or scalar arrays; `headers` accepts non-null scalars. Strings are sent unchanged, booleans as `true`/`false`, and numbers with canonical JSON v1 notation, preserving int64 precision. Query and form values are URL-encoded: spaces become `+`, arrays repeat a name in input order, and empty arrays contribute no fields. Fields are ordered by UTF-8 key bytes. Missing optional bindings omit their field; explicit null is preserved by JSON and rejected before sending by text/query/header/form/file bindings.

Header names are case-insensitive: duplicates within or between source and executor maps fail even when values match. Host, Authorization and connection-control overrides are forbidden. Header CR/LF is rejected. When a body is configured, Content-Type, Content-Length and Transfer-Encoding are Agent-managed and cannot also appear in either header map.

### Request bodies

Omitting `body` sends zero body bytes; the Agent adds no body Content-Type, Content-Length or Transfer-Encoding. Standard HTTP framing may still add `Content-Length: 0` for POST/PUT/PATCH. A whole-body `input` Pointer must be guaranteed present, including every ancestor and array index.

| `body.kind` | Configuration and upstream encoding |
|---|---|
| `json` | Exactly one of `fields` (name → binding map), `input` (whole-value Pointer), or `value` (fixed JSON). Object/array/scalar/null retain their shape. Sends canonical JSON v1 UTF-8 with `application/json`, no BOM or appended newline |
| `form` | Required `fields` map using query scalar/array rules; sends `application/x-www-form-urlencoded` |
| `multipart` | Required ordered `parts` array. Each part has a fixed `name`, `kind: text/json/file`, and one input/value binding. Text sends the scalar text as `text/plain; charset=utf-8`; JSON sends canonical JSON as `application/json`; file accepts only input file/file arrays, with optional fixed `content_type` |
| `file` | Required `input` to one required file; sends its original bytes with optional fixed `content_type`, otherwise the validated input MIME |

Multipart names cannot be repeated in configuration. File arrays expand to repeated same-name parts in array order; empty arrays and missing optional files contribute no parts. File names come from validated input metadata, and `content_type` overrides only the MIME. Text/JSON parts have no filename. The Agent creates the boundary and Content-Disposition; callers cannot supply multipart headers. For example:

```yaml
body:
  kind: multipart
  parts:
    - {name: item, kind: text, input: /item}
    - {name: attachment, kind: file, input: /documents}
```

Declare `documents` with `items: {type: file}` for multiple attachments. Onprest's [one-call file input forms](/api/files#file-input) are independent of this upstream encoding: REST JSON, REST multipart and MCP can all feed the same HTTP executor.

The complete request is spooled and validated before any HTTP send. `executor.limits.max_http_request_bytes` and `max_http_response_bytes` each default to `32MiB`; request size includes multipart framing. Query/header/control metadata is bounded to `64KiB`. Request and response temporary files share `runtime.spool_total_bytes`. A pre-send input or capacity failure has `outcome: not_started`.

### Responses and redirects

`response.kind: json` parses one strict JSON value, then applies common output selection/validation without a DB `rows/count` wrapper. Use `output.data: {}` to publish it, or an explicit `files.format: csv` to generate CSV from an object array. `response.kind: file` uses the response bytes unchanged; `response.filename` defaults to `response.bin` and `mime_type` to `application/octet-stream`. Add `output.files: {}` to publish it; an output MIME override takes precedence. [File delivery](/api/files) supplies reference, REST direct or MCP inline delivery. Upstream headers and error bodies are not forwarded.

`success_statuses` is a nonempty explicit set, defaulting to 200–299. Other statuses produce a safe `EXECUTION_FAILED` with reason `UPSTREAM_HTTP_STATUS`. Malformed JSON or output mismatch produces `OUTPUT_INVALID`; byte/structure/quota excess produces `LIMIT_EXCEEDED`. Full response validation completes before any success or partial result is published.

`response.redirect` defaults to `{enabled: false, max_hops: 3}`. When enabled, 301/302/303/307/308 redirects retain the configured method and completed body, including for POST; they do not switch to GET. Each hop must stay at the source origin and pass method, DNS/IP, credential and hop-limit checks. No failure is automatically retried.

The one `policy.timeout` budget covers construction, all hops, response reading and output validation. HTTP status and `executor.effects: none` are not evidence of rollback or safe retry. Effects default to `possible`; after a request is sent, a failure can have `outcome: unknown`. Keep application-specific retry decisions outside automatic transport behavior.

## File reads and CSV output

A file capability selects completed files under a prepared folder root. Relative roots resolve from the configuration directory. This excerpt supplements the required `schema_version: 1` and Gateway signing configuration:

```yaml
sources:
  folders:
    reports:
      root: ./reports
      access: read
capabilities:
  download_report:
    executor:
      type: file
      read:
        source: reports
        selector:
          name: report.pdf
    output:
      files:
        mime_type: application/pdf
        delivery:
          rest: reference
          mcp: reference
```

The `executor.read.selector` settings are:

| Setting | Default | Values and meaning |
|---|---|---|
| `path` | `.` | Fixed relative directory under the folder root; parent traversal is rejected |
| `name` | unset | Fixed basename or `{input: /filename}` pointing to a required, non-null string input |
| `name_regex` | unset | Go regular expression, 1–4096 bytes, matched against the entire basename; case-folding flags are rejected |
| `recursive` | `false` | Whether to include descendant directories |
| `sort` | `{by: name, order: asc}` | Object with `by: name`, `modified_at` or `size`, and `order: asc` or `desc` |
| `take` | `1` | Positive integer limiting selected files; REST direct requires omitted `output.data` and, for original file output, `take: 1` |
| `scan_limit` | `10000` | Positive integer bounding all inspected entries across the request, including nonmatches, directories and reserved names |

Exactly one of `name` and `name_regex` is required. Names are case-sensitive basenames without Unicode normalization. Equal sort values use ascending root-relative UTF-8 path order before applying `take`. Exceeding `scan_limit` returns `LIMIT_EXCEEDED` without a partial selection; no matching files returns `NOT_FOUND`. Symlinks, hardlinks, special files, filesystem boundaries and reserved temporary names are rejected. Complete producer writes in a private temporary file and atomically rename into the selected completed name. Preparation validates and fixes folder roots without saving business files; `validate` and `doctor` keep their non-destructive behavior. File inputs and `executor.write` use the same schema and prepared folder roots; see [File writes](#file-writes) and [File input](/api/files#file-input).

DB SELECT and CSV capabilities can generate CSV from the same selected and validated rows:

```yaml
output:
  data: {}
  items:
    properties:
      id: {type: integer}
      name: {type: string}
  files:
    format: csv
    filename: customers.csv
    columns: [id, name]
    delivery: {rest: reference, mcp: reference}
```

Omit `data` to return files only. Declared columns fix CSV order; excluded data is excluded from generated CSV. An empty result still includes the header. Integer precision is preserved, and cells that could be interpreted as spreadsheet formulas are escaped by default (`formula_escape: true`). File reads return original bytes and cannot request CSV generation.

File policy limits are `max_output_file_bytes` (default `32MiB`), `max_total_output_file_bytes` (`64MiB`), `max_output_files` (`16`), and `file_ttl` (`15m`). `mcp_inline_total_bytes` applies only to inline MCP delivery and defaults to `1MiB`. `runtime.transfer_timeout` defaults to `60s`, at most `300s`; it bounds one download or all inline files in one tool result. See [File Output](/api/files) for delivery and lifetime rules and [Gateway Configuration](/gateway/configuration#file-reference-origin) for the required reference origin.

## Metadata

`description`, explicit boolean `annotations`, and validated `examples.params` describe a capability. Field descriptions belong in `input.properties.<name>.description`, DB SELECT/CSV `output.items.properties.<column>.description`, or DML `output.properties.<name>.description`. OpenAPI 3.1 and MCP input/output schemas derive from the same compiled contract. SQL, source connection details, secrets and hidden capabilities are not advertised. Examples appear in OpenAPI; MCP uses annotation hints and advertises outputSchema only for protocol versions that support it.

## Wasm executors

Use `executor.type: wasm` with a `module` path relative to the configuration directory, optional SHA-256 `sha256` (when specified, a nonempty string of exactly 64 lowercase hexadecimal characters), and `effects: none` or `possible` (default). The Agent validates the module's `onprest` custom metadata, host ABI version, imports and limits during startup, `validate` and `doctor`, without running business code. Deploy the completed module with the Agent; the installation needs no Go compiler or separate Wasm runtime. See the [host ABI example](https://github.com/viewlegacy/onprest/tree/dev-2.0.0/examples/wasm).

### Permissions and paths

`sandbox.enabled` defaults to false: code uses the Agent OS user's filesystem/network permissions and prepared process environment without named sources or grants. When false, omit the entire `permissions` field, including an empty map. With true, permissions default to deny-all. `permissions.filesystem` entries have `root` (config-relative or absolute) and `access: read` or `read_write`. Links, reparse points, filesystem crossings and unsafe file types are rejected. `permissions.http` grants specify exact `origin`, `methods`, segment-boundary `path_prefix`, and optional `allowed_cidrs`. HTTPS verifies the destination hostname and system trust; ambient proxies are ignored. `permissions.environment` lists allowed names. Uploaded input handles remain available only to their owning request, including in deny-all mode.

The FS bridge supports regular files and directories; device, FIFO and socket files are rejected in both modes. Relative business paths resolve from the configuration directory. The module's `PWD` is fixed to that directory in both modes as runtime cwd plumbing, including when no environment names are allowed; other environment values follow the mode above. On Windows, WASI uses an absolute guest path such as `/volumes/C/service` for `C:\service`, or `/unc/server/share/service` for a native UNC base. Native host paths are normalized and authorized by the Agent; guest mapping alone grants no access. These effective values and module bytes are captured during preparation and do not change during execution.

### Limits

Set Wasm limits under `executor.limits`; every value must be positive.

| Setting | Default |
|---|---|
| `memory_bytes` | `128MiB` |
| `max_module_bytes` | `32MiB` |
| `max_handles` | `64` |
| `max_host_calls` | `8` |
| `max_file_read_bytes` / `max_file_write_bytes` | `64MiB` each |
| `max_total_file_read_bytes` / `max_total_file_write_bytes` | `256MiB` each |
| `max_file_operations` | `65536` |
| `max_http_request_bytes` / `max_http_response_bytes` | `32MiB` each |

`memory_bytes` must be between 64KiB and 4GiB, inclusive. Each single-file read/write limit must be no greater than its corresponding total limit. Common input/output policy limits also apply. FS and input reads/writes reserve bytes before I/O, charge actual bytes and logical growth, and keep cumulative totals across reopen/seek. Known-length writes reserve before truncation; metadata and failed operations are bounded too. Close and cancellation remain available after quota exhaustion.

### WASI file behavior

Standard WASI file I/O uses the same authorization and budgets as the host bridge. In sandbox OFF, removal and rename operate on the final symlink itself (including dangling links), and directory creation follows ordinary directory symlinks. Special file objects are rejected before mutation or blocking I/O.

File effects reflect observed creation, truncation or writing; opening an existing file with a create flag alone leaves it unchanged. Open directory descriptors retain their target through path renames and replacements, including rewind. Positioned reads and writes preserve the descriptor offset and count as one file operation. Read-only file and directory sync operations use the OS result without consuming write bytes or creating effects.

Linux `fd_allocate` reserves the requested region and logical growth before native allocation; allocation is unsupported on macOS and Windows. Unmetered link, symlink, readlink, timestamp and advise operations return unsupported. Host errors use fixed categories (invalid, permission denied, not found, limit exceeded, canceled, I/O, unsupported, already exists) without OS paths or raw detail.

### HTTP and results

HTTP sends only after the complete request body is ready, never retries or follows redirects automatically, and exposes response status and bytes. Valid raw result ABI application terminals follow the [shared error contract](/api/errors), with explicitly public messages and observed outcomes. Review the [code security boundary](/security#wasm-code-boundary).
