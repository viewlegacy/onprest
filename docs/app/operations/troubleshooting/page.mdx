# Troubleshooting

## Agent Cannot Connect

Check:

- `gateway.url` points to `/ws/agent`.
- If a reverse proxy or load balancer is used, it supports WebSocket upgrade.
- `GATEWAY_AGENT_PUBLIC_KEY` matches `gateway.agent_private_key`.
- agent host can make outbound connections to gateway.
- timestamp skew is not outside the allowed signing window.

The gateway returns `AUTH_FAILED` before WebSocket establishment when signature validation fails.

## Run the doctor probe

After the Gateway is running, use `doctor` to separate local preparation failures from Gateway transport and authentication failures:

```bash
onprest-agent doctor --config /absolute/path/capability.yaml --format json
```

Use the first failed check to choose the next action:

- `config` or `database_*`: correct `capability.yaml` or restore database access.
- `gateway_dns` or `gateway_connect`: check the configured hostname, port, DNS, firewall, and proxy path.
- `gateway_tls`: check the hostname, SNI certificate, and the Agent host's OS trust store. There is no separate Gateway CA setting.
- `gateway_challenge` or `gateway_verify`: check proxy routing, clock synchronization, and that `GATEWAY_AGENT_PUBLIC_KEY` matches `gateway.agent_private_key`.

Later dependent checks are shown as `skipped`. Doctor does not establish or replace the normal WebSocket connection and does not execute a capability. See the [CLI Reference](/reference/cli#diagnose-agent-and-gateway) for output and exit codes, and [Agent Local Logs](/agent/local-logs) for the latest-failure log.

## Private spool recovery prevents startup

Keep `runtime.spool_dir` private, writable by the Agent user, and dedicated to one Agent process. Another process holding its lock, invalid cleanup records, an unavailable recorded save directory, an identity/permission mismatch, or insufficient spool quota for unrecovered records prevents startup. Preserve the spool and recorded directories, and inspect the Agent's [local startup diagnostic](/agent/local-logs) before correcting access or restoring the directory. After restoring access or correcting permissions or quota, restart the Agent using the same spool path. `validate` and `doctor` do not open or recover the running spool.

Startup recovers recorded unfinished saves before connecting, even if the current source configuration has changed. Before moving or deleting a spool that contains cleanup records, complete recovery at its original path. Do not edit those records or delete business files by an `.onprest-*` prefix scan. Recovery removes only verified recorded temporary names and retains completed business files.

## OpenAPI Returns 503

`AGENT_OFFLINE` means gateway has no connected agent or no usable OpenAPI cache.

## Mutation outcome is unknown

Inspect `error.outcome` rather than inferring transaction state from `EXECUTION_TIMEOUT` or another error code. `unknown` means completion is unconfirmed, including after an in-flight disconnect: do not retry automatically. Check the target record using an independent read capability and inspect the agent-local detail log. `rolled_back` means the Agent confirmed rollback of the business effects. `not_started` means execution did not begin.

For `LIMIT_EXCEEDED` with `rolled_back`, inspect the configured input/output capacity and, for DML, `policy.max_affected_rows` and the SQL's target conditions before adjusting a limit. If the outcome is `unknown`, use the same independent-read reconciliation procedure. Error responses do not include an affected count; the Gateway request log has `count: null`.

See [Mutation Reconciliation](/operations/mutation-reconciliation) for the read-capability workflow and an INSERT example.

Check agent startup logs and `onprest-agent.log`. DB ping or EXPLAIN failure prevents the agent from connecting.

## API Key Authentication Fails

Check:

- Header is `Authorization: Bearer ...` or `X-API-Key`.
- `GATEWAY_API_KEYS_JSON` contains the bcrypt hash from `create-key`.
- The JSON value was single-quoted when sourced by shell.
- The key was not copied from the masked/logged form.

## Capability Denied

`CAPABILITY_DENIED` means the API key is valid but not authorized for that capability.

Update the key definition or use a key whose `capabilities` includes the requested capability or `"*"`.

## DB Ping or EXPLAIN Startup Failure

Agent stops before connecting to gateway. Check `onprest-agent.log` next to the agent binary.

To check an edited configuration without stopping a running Agent, run:

```bash
onprest-agent validate --config /absolute/path/capability.yaml
```

For database-open, Ping, EXPLAIN, or similar recorded failures, inspect only the detail-log path returned by that invocation; it is not the runtime `onprest-agent.log`. Text output identifies it with `see validation detail log`, while JSON uses `detail_log`. Configuration and busy failures are fully reported by the CLI and return no log path. If the CLI reports that the diagnostic could not be recorded, it deliberately omits `detail_log`; do not use an older fixed log as the current diagnostic. A JSON `cleanup_path` names only an incomplete temporary file and may be removed after validation exits.

Do not edit or remove the validation lock file. If another validation is running, wait for it to finish. See [Agent Local Logs](/agent/local-logs) for the authoritative fixed-file, temporary-file, recovery, size, and access-control rules. Check any diagnostic before sending it to support.

Validation success covers YAML lint, DB Ping, and startup EXPLAIN. It does not cover Gateway reachability, real capability results, data-dependent constraints, or trigger runtime behavior.

Common causes:

- DB host or port unreachable.
- DB credentials are invalid.
- DB user lacks required permissions.
- SQL syntax is invalid for the configured driver.
- SQL Server plan validation permissions are missing.

## Runtime DB Permission Failure

External callers receive a normalized agent error such as `EXECUTION_FAILED`. The DB-specific detail is in `onprest-agent.log`.

This is expected. Do not look for SQL detail in gateway stdout or HTTP responses.

## Rate Limited

`RATE_LIMITED` is shared by several rejection layers. Use the fixed public message and related logs to identify the layer:

| Public message | Rejection layer and action |
|---|---|
| `too many requests` | Gateway source-IP limiter, before authentication/Agent execution. Review `GATEWAY_RATE_LIMIT_REQUESTS_PER_SECOND`, `GATEWAY_RATE_LIMIT_BURST`, and trusted-proxy source-IP detection. REST request or MCP `mcp_http_rejected` logs record this HTTP rejection. |
| `authentication is busy; retry later` | Gateway authentication capacity, before Agent execution. Inspect concurrent authentication load; changing capability rate policy does not affect this limit. |
| `capability rate limit exceeded` | Agent capability admission, before its execution queue. Review the capability's `policy.rate_limit` or inherited defaults and call rate. The Gateway request event and sampled Agent-local rejection log identify the capability. |

All use `not_started`; the code alone does not select Gateway env or capability policy. See [Capability YAML](/agent/capability-yaml#policy), [Gateway Logs](/gateway/logs), and [Errors](/api/errors).

## File references are unavailable

If a capability call returns `DEPENDENCY_UNAVAILABLE` naming `ONPREST_PUBLIC_BASE_URL`, set the explicit [reference origin](/gateway/configuration#file-reference-origin) and restart Gateway. Metadata requiring references is not advertised until this setting is available. Ensure the reverse proxy also routes `/api/v1/files/`.

Use the same API credential as the business call. A different credential receives HTTP 403; that rejected request leaves the live reference unchanged, so the original credential can still download it. Expired TTL, credential rotation, definition change, Agent reconnect or either binary restart invalidates a handle. Downloads do not rerun the business call.

If a handle has expired or otherwise become invalid, obtaining a replacement requires an explicit new call; consider that call's business effects before retrying. `BUSY` can mean another transfer for the same result is active. A truncated response or transport error is a failed download even if HTTP headers were already sent. See [File Output](/api/files).

## Docker or Testcontainers Issues

Container-backed integration tests require Docker daemon access.

Use mandatory mode when skips should fail the gate:

```bash
ONPREST_IT_REQUIRE_CONTAINERS=1 make test-it-release-gate
```

If tests fail after interruption, check for leftover testcontainers resources and rerun the release gate. See [Test Commands](/reference/test-commands) for the meaning of `ONPREST_IT_REQUIRE_CONTAINERS` and the full command list.
