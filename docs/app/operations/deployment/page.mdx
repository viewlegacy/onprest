# Deployment

Onprest OSS deployment is the gateway binary plus the agent binary.

## Deployment Units

| Unit | Where it runs | Required files |
|---|---|---|
| `onprest-gateway` | public or private server reachable by clients and agent | gateway env |
| `onprest-agent` | on-prem or DB-adjacent environment | `capability.yaml` |

The repository does not need to be deployed from source. Release archives are the normal binary installation path; locally built artifacts can also be copied to another directory or host.

## Supported Operating System Baseline

| OS | Architectures | Minimum |
|---|---|---|
| Linux | `amd64`, `arm64` | A kernel supported by Go 1.26 |
| Windows | `amd64` | Windows 10 or Windows Server 2016 |
| macOS | `amd64`, `arm64` | macOS 12 |

These are the officially supported baselines. Earlier versions may run, but they are not covered by the compatibility guarantee. Validate the exact release binary in the target environment before deploying to an older legacy system.

Cross-building proves only that artifacts can be produced. See [Release Gate](/operations/release-gate) for the native runtime evidence required before release.

## Binary Release Installation

Each GitHub release provides one archive for every supported OS/CPU target. Unix
archives use `.tar.gz`; Windows uses `.zip`. Every archive contains both
`onprest-gateway` and `onprest-agent`, `LICENSE`, `INSTALL.md`, minimal
`gateway.env.example` and `capability.yaml.example` files,
`RELEASE-MANIFEST.txt`, and a dependency report for each binary. These
configuration files are incomplete production templates: add a reviewed
capability and replace all placeholders before using them.

| Host | Architecture | Release asset |
|---|---|---|
| Linux | `amd64` | `onprest-X.Y.Z-linux-amd64.tar.gz` |
| Linux | `arm64` | `onprest-X.Y.Z-linux-arm64.tar.gz` |
| macOS | Intel (`amd64`) | `onprest-X.Y.Z-darwin-amd64.tar.gz` |
| macOS | Apple silicon (`arm64`) | `onprest-X.Y.Z-darwin-arm64.tar.gz` |
| Windows | `amd64` | `onprest-X.Y.Z-windows-amd64.zip` |

Each release also provides `onprest-X.Y.Z-quickstart.tar.gz`, the example files
for the [Quick Start](/quick-start). It contains public development credentials
and is not used for production installation. Every archive is also published
under a name without the version, such as `onprest-linux-amd64.tar.gz`, so
`https://github.com/viewlegacy/onprest/releases/latest/download/<name>` always
points to the latest release.

Download the archive for your host from the
[GitHub Releases](https://github.com/viewlegacy/onprest/releases) page and
extract it. To verify a download, save `SHA256SUMS` from the same release next
to it and run:

```bash
sha256sum --check --ignore-missing SHA256SUMS   # macOS: shasum -a 256 --check --ignore-missing SHA256SUMS
gh attestation verify onprest-X.Y.Z-linux-amd64.tar.gz --repo viewlegacy/onprest
```

On Windows, compare `(Get-FileHash onprest-X.Y.Z-windows-amd64.zip).Hash` with
the matching line in `SHA256SUMS`. Attestation verification uses the
[GitHub CLI](https://cli.github.com/) and can run on any computer, not only the
installation host.

After extraction, continue with the bundled [`INSTALL.md`](https://github.com/viewlegacy/onprest/blob/main/release/INSTALL.md). It maps the generated
keys into the two configuration files and gives Unix and Windows commands for
validation and startup.

## New Customer Setup

1. Generate an agent key pair with `onprest-gateway create-agent-secret`.
2. Generate one or more API keys with `onprest-gateway create-key`.
3. Create a customer-specific `gateway.env`.
4. Start a dedicated gateway process for the customer.
5. Deliver `onprest-agent` and a `capability.yaml` template to the on-prem environment.
6. Fill in gateway URL, agent private key, DB credentials, and capabilities.
7. Run `onprest-agent validate --config PATH` against the completed file.
8. Start the agent.
9. Verify `/healthz`, `/openapi.json`, REST, and MCP.

## Binary Deployment

This is the primary deployment path for legacy environments without Docker.

```bash
set -a
. ./gateway.env
set +a
./onprest-gateway
```

```bash
./onprest-agent --config ./capability.yaml
```

The Gateway reads process environment variables; it does not read
`gateway.env` itself. On Windows PowerShell, copy the configured values into the
process environment (or the service environment) before starting it:

```powershell
$env:GATEWAY_AGENT_PUBLIC_KEY = '<generated-agent-public-key>'
$env:GATEWAY_API_KEYS_JSON = '[{"name":"operator","key_hash":"<generated-key-hash>","capabilities":["get_customer"]}]'
.\onprest-gateway.exe
```

In another PowerShell session, validate and start the Agent:

```powershell
.\onprest-agent.exe validate --config .\capability.yaml
.\onprest-agent.exe --config .\capability.yaml
```

Keep the agent binary and `capability.yaml` together. Agent local logs are written next to the agent binary.

## Self-Hosted Minimal Settings

For a self-hosted gateway, configure at least:

```env
GATEWAY_AGENT_PUBLIC_KEY=base64url-ed25519-public-key
GATEWAY_API_KEYS_JSON='[{"name":"internal","key_hash":"$2a$10$xxxxx","capabilities":["*"]}]'
```

Then decide whether to set:

- `GATEWAY_ADDR` when the default listen address `:8080` is not suitable.
- `GATEWAY_PUBLIC_URL` for reverse proxy or load balancer deployments so OpenAPI `servers` points at the external URL.
- `GATEWAY_CORS_ALLOWED_ORIGINS` when browser-based clients on another origin need to call gateway directly.
- `GATEWAY_IP_ALLOW_LIST` for caller IP restrictions.
- `GATEWAY_TRUSTED_PROXY_CIDRS` when running behind a reverse proxy or load balancer.
- `GATEWAY_RATE_LIMIT_REQUESTS_PER_SECOND` and `GATEWAY_RATE_LIMIT_BURST` for per-source rate limiting.
- `GATEWAY_EMIT_OPENAPI_SNAPSHOT=true` only when an operator needs the full OpenAPI document on gateway stdout for collection.
- `GATEWAY_MAX_REQUEST_BODY_BYTES` when the default 1 MiB REST/MCP request body limit is unsuitable. Set a positive integer byte count and restart the gateway.

For the agent, configure `capability.yaml` and pass it with `--config`. If `--config` and `AGENT_CAPABILITY_FILE` are both omitted, the agent reads `capability.yaml` next to the `onprest-agent` binary. `AGENT_CAPABILITY_FILE` remains available for environments that prefer env-based configuration:

```env
AGENT_CAPABILITY_FILE=/path/to/capability.yaml
```

Production `gateway.url` values must use `wss://.../ws/agent`. Plain `ws://` is accepted without an override only on loopback for local development. The `allow_insecure_non_loopback_ws` acknowledgement exists for isolated development networks, not production deployment.

The challenge-based `onprest-agent-v2` handshake requires matching gateway and agent releases. An old agent cannot authenticate to a new gateway, and a new agent cannot obtain a challenge from an old gateway. Schedule the two binaries as one coordinated upgrade.

For OS-managed binary operation, follow the separate [new-service installation and existing-service change procedures](/operations/capability-changes). They validate the exact registered file before starting or stopping a service and include post-start health, OpenAPI, REST, and MCP checks. See [CLI Reference](/reference/cli#agent-service-commands) for individual service command syntax and aliases. Service installation does not enable automatic start on OS boot; configure that separately with the host OS if required.

When the agent runs as an OS service, stdout/stderr are handled by the service manager. On macOS service installs, process events go to `/var/log/onprest-agent.stdout.log` and fatal stderr output goes to `/var/log/onprest-agent.stderr.log`. DB-specific detail still belongs in `onprest-agent.log` next to the agent binary.

### Database TLS certificate rotation

Database TLS CA and client certificate files are loaded when the Agent creates the DB pool. Use an overlap period so the old and new material are both accepted until the new connection is verified.

For a private-CA rotation, first deploy a trust bundle containing both the old and new CA, run `onprest-agent validate --config PATH`, and restart the Agent through the host service manager. Rotate the database server certificate, confirm a capability call, and only then remove the old CA from the bundle and validate and restart again. For a client-certificate rotation, configure the database to accept both the old and new certificates or issuing CAs during the overlap, atomically replace the Agent certificate and key, validate and restart, confirm a capability call, and then revoke the old certificate or CA. If the database cannot provide an overlap period, schedule a coordinated maintenance window instead.

Do not retire old trust or credentials until the post-restart capability check succeeds. A failed CA, expiry, or hostname check stops the connection; the Agent does not retry with a weaker mode or plaintext.

## Docker Optional Usage

Docker images and Docker Compose are supported operational paths, but Docker is not required by the OSS core. Container env-file handling must preserve `GATEWAY_API_KEYS_JSON` and bcrypt `$` characters.

```bash
docker build --build-arg TARGET=gateway -t onprest-gateway .
docker build --build-arg TARGET=agent -t onprest-agent .
```

For a release build, pass the same `--build-arg VERSION=x.y.z` to both commands. An omitted value is reported as `dev` by the binaries and MCP `initialize` metadata.

When running the agent container, mount `capability.yaml` and pass it to the container entrypoint:

```bash
docker run --rm -v "$PWD/capability.yaml:/config/capability.yaml:ro" onprest-agent --config /config/capability.yaml
```

The mounted `capability.yaml` must use database and gateway addresses reachable from inside the container. Container platforms manage process start/stop and stdout/stderr collection. Do not use `onprest-agent service install` inside a container. `docker-compose.yml` is a convenience for local or container-based evaluation, not a required production deployment model.

## Deployment Boundary

This page covers deployment of the two OSS binaries only. Managed products and their operating policies are outside the OSS core and are not deployment requirements for `onprest-gateway` or `onprest-agent`.
