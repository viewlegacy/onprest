# Deployment

Onprest runs as two binaries: a Gateway reachable by API clients and an Agent
near the database. The Agent connects outbound to the Gateway. Neither host
needs the source repository, Go, Docker, or a native database client runtime.

## Binary Release Installation

Open the [GitHub Releases](https://github.com/viewlegacy/onprest/releases) page
and download the archive for each host. A Gateway and Agent from the same
release must be used together.

| Host | Release asset |
|---|---|
| Linux amd64 | `onprest-X.Y.Z-linux-amd64.tar.gz` |
| Linux arm64 | `onprest-X.Y.Z-linux-arm64.tar.gz` |
| macOS Intel | `onprest-X.Y.Z-darwin-amd64.tar.gz` |
| macOS Apple silicon | `onprest-X.Y.Z-darwin-arm64.tar.gz` |
| Windows amd64 | `onprest-X.Y.Z-windows-amd64.zip` |

Extract the archive with your OS archive tool. It contains both binaries,
`LICENSE`, two configuration templates, and `INSTALL.md`. For example:

```bash
tar -xzf onprest-X.Y.Z-linux-amd64.tar.gz
cd onprest-X.Y.Z-linux-amd64
```

On Windows, use **Extract All** or `Expand-Archive`, then open the extracted
directory. The separate `onprest-X.Y.Z-quickstart.tar.gz` asset contains public
development credentials and a disposable database setup. It is for the
[Quick Start](/quick-start), not production configuration.

`SHA256SUMS` and GitHub artifact attestations are also published for operators
who choose to verify downloads. Verification is optional for installation;
GitHub's [attestation guide](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations#verifying-artifact-attestations-with-the-github-cli)
explains how to check build provenance.

## Configure and Start

The included `gateway.env.example` and `capability.yaml.example` are starting
points, not ready-to-run production credentials or capabilities. Follow the
bundled `INSTALL.md` to:

1. Generate an Agent key pair and a capability-scoped API key with
   `onprest-gateway create-agent-secret` and `onprest-gateway create-key`.
2. Fill in the Gateway environment and the Agent's Gateway URL and database
   connection. Add at least one reviewed capability to the YAML.
3. Run `onprest-agent validate --config PATH` against the completed file.
4. Start the Gateway and Agent, then check `/healthz` for
   `"agent_connected": true` before calling REST or MCP.

On Unix, the two processes can be started in separate terminals:

```bash
set -a
. ./gateway.env
set +a
./onprest-gateway
```

```bash
./onprest-agent --config ./capability.yaml
```

The Gateway reads process environment variables; it does not read
`gateway.env` itself. The bundled `INSTALL.md` includes PowerShell commands.
For an OS-managed Agent, follow [Capability Changes](/operations/capability-changes)
for installation and later updates. The service does not enable automatic start
on OS boot; configure that through the host OS if needed.

## Supported Hosts

| OS | Architectures | Minimum |
|---|---|---|
| Linux | `amd64`, `arm64` | A kernel supported by Go 1.26 |
| Windows | `amd64` | Windows 10 or Windows Server 2016 |
| macOS | `amd64`, `arm64` | macOS 12 |

Cross-building alone does not establish native runtime compatibility. Before
deploying to an older legacy host, check its OS against the baseline above and
test the chosen binary there.

## Network and Database Settings

Production Agent connections use `wss://.../ws/agent`; loopback `ws://` is
available for local development. The Gateway may be directly exposed or placed
behind a compatible [reverse proxy](/gateway/reverse-proxy). TLS termination is
an operator choice, not an Onprest dependency.

Use [Gateway Configuration](/gateway/configuration) for listen address, API
keys, proxy, CORS, and rate-limit options. Use [Capability YAML](/agent/capability-yaml)
for database connection, SQL, and policy fields. Give the Agent's database user
only the privileges its capabilities need.

### Database TLS Certificate Rotation

Database TLS CA and client certificate files are loaded when the Agent creates
its DB pool. For a CA rotation, make the Agent trust both old and new CAs,
validate and restart it, rotate the database certificate, and confirm a
capability call before removing the old CA. For a client-certificate rotation,
make the database accept both certificates during the change, replace the
Agent certificate and key, validate and restart, and confirm a call before
revoking the old certificate. If an overlap is impossible, use a coordinated
maintenance window. Certificate verification failures do not fall back to
plaintext.

## Docker Is Optional

Docker images are available for container-based deployments, but the two
binaries are the primary deployment units. Build a container image from the
repository only if that matches your environment:

```bash
docker build --build-arg TARGET=gateway -t onprest-gateway .
docker build --build-arg TARGET=agent -t onprest-agent .
```

For a release image, pass the same `--build-arg VERSION=x.y.z` to both builds.
When running the Agent in a container, mount the completed `capability.yaml`
and use Gateway and database addresses reachable from inside the container.
Use the container platform—not `onprest-agent service install`—to manage that
process.
