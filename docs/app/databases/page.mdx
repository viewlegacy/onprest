# Databases

Onprest supports PostgreSQL, MySQL, SQL Server, and Oracle through the agent.

The Gateway does not need database credentials or driver configuration. The
Agent connects to the selected database and checks each capability's SQL
before making it available through REST or MCP.

## Least Privilege

Use a DB user with the narrowest permissions needed for the defined capabilities.

For read capabilities:

- Prefer read-only users.
- Grant access only to required schemas, tables, views, or stored objects.
- Keep DB credentials only in `capability.yaml` on the agent side.
- Do not encode DB credentials in gateway env or API clients.

YAML `policy.readonly` is a guardrail, not a replacement for DB permissions.

For mutation capabilities, grant only the required operations on the required tables. Native `RowsAffected()` is returned unchanged, so DB/driver-specific upsert semantics are intentional. Startup EXPLAIN validates syntax, objects, placeholders, and many permission failures without executing the target mutation; it does not validate data-dependent constraints or runtime trigger behavior.

## Startup Verification

The agent verifies capabilities before connecting to the gateway.

| Check | Purpose |
|---|---|
| DB ping | Fail fast when the database is unreachable |
| EXPLAIN | Catch invalid SQL before exposing the capability |
| YAML lint | Reject invalid driver, policy, params, result, or logging settings |

If startup fails, check the Agent output and its local log. The standalone
`onprest-agent validate` command reports its own diagnostic path when a
database check fails; see [Troubleshooting](/operations/troubleshooting).

## Database TLS

The agent creates each database connection from the `database` section of `capability.yaml`.

| Driver | TLS support |
|---|---|
| `postgres` | `disable`, `require`, `verify-ca`, or `verify-full`; optional client certificate authentication |
| `mysql` | `disable`, `require`, or `verify-full`; optional client certificate authentication |
| `sqlserver` | `disable`, encrypted-but-unverified `require`, or CA/hostname-verified `verify-full` |
| `oracle` | `disable`, `require`, or `verify-full`; no Oracle Instant Client or native Oracle runtime |

TLS defaults to `disable`. All four drivers support encryption-only `require` and identity-verifying `verify-full`; only PostgreSQL also supports `verify-ca`. `verify-full` uses the OS trust store when `ca_file` is omitted and verifies `server_name` or the connection host. Unsupported fields and modes are rejected at startup, and a failed verification never falls back to plaintext. Client certificates are supported only by PostgreSQL and MySQL.
