# CLI Reference

Provisioning commands are exposed by `onprest-gateway`.

## Version

Both binaries use the same embedded build version. The `version`, `--version`, and `-v` forms print one line and exit successfully:

```bash
./onprest-gateway --version
./onprest-agent --version
```

Uninjected development binaries print `dev`. Set `VERSION=x.y.z` for `make build` or `make build-cross` to inject the same release version into both binaries. The Gateway also returns this value as MCP `initialize.serverInfo.version`.

## Generate Agent Secret

```bash
./onprest-gateway create-agent-secret
```

Outputs an Ed25519 private key and public key.

- private key: `capability.yaml` `gateway.agent_private_key`
- public key: `gateway.env` `GATEWAY_AGENT_PUBLIC_KEY`

Command alias:

```bash
./onprest-gateway create-agent
```

## Generate API Key

```bash
./onprest-gateway create-key --name internal --capabilities "*"
./onprest-gateway create-key --name partner-a --capabilities "get_customer,get_orders"
```

The command outputs a plaintext API key and bcrypt `key_hash`. Store only the hash in `GATEWAY_API_KEYS_JSON`. Give the plaintext key to the caller once.

## Start Agent

```bash
./onprest-agent --config ./capability.yaml
```

`--config` selects the capability YAML file. If omitted, the agent checks `AGENT_CAPABILITY_FILE`, then falls back to `capability.yaml` next to the `onprest-agent` binary.

`--capability-file PATH` is an alias for `--config PATH`. When both are supplied, `--config` takes precedence.

## Build and test Wasm code

Use the Agent binary on the author machine to build a Go WASI command package, inspect a module without running it, and execute one configured Wasm capability locally:

```sh
onprest-agent code build --output ./module.wasm --source ./code
onprest-agent code build --config ./agent.yaml --capability process_document --source ./code
onprest-agent code validate --module ./module.wasm --format json
onprest-agent code test --config ./agent.yaml --capability process_document --params '{"customer":"Alice"}' --format json
onprest-agent code test --build --config ./agent.yaml --capability process_document --source ./code --force --params-file ./params.json
```

Build requires Go 1.26.9 or later and a package `main` in a Go module. `--source` defaults to the current directory; it selects that package directory, without searching for another entry point. Normal Go file selection applies, including OS/build constraints and exclusion of test functions. Build copies the environment with `GOOS=wasip1 GOARCH=wasm CGO_ENABLED=0 GOWORK=off` and runs `go build -trimpath -mod=readonly` with private copied module/checksum files; relative local replacements retain the original module base, and it does not run generate or update source, `go.mod`, or `go.sum`. `--offline` also sets `GOPROXY=off GOTOOLCHAIN=local GOSUMDB=off`, so missing dependencies or a missing suitable local compiler fail.

Standalone build requires `--output`; capability build requires both `--config` and `--capability` and rejects `--output`. Capability build lints the complete YAML and selects a Wasm capability, even when its module does not exist yet. CLI paths are relative to the current directory; YAML module paths are relative to the config file. Build and local test do not connect to the Gateway, read its signing key file, open unrelated sources, or use the running Agent's spool or detail log. The YAML's deployment configuration must still pass ordinary syntax and consistency checks.

Build adds the `onprest` ABI/minimum-Agent/import custom section and verifies actual imports, signatures, module size and any configured `executor.sha256` without executing business code. It writes the module and adjacent `FILE.manifest.json`, publishing the manifest last. The manifest has `sha256`, `abi`, `compiler_version`, `dependency_hash`, and sorted `required_imports`. `dependency_hash` is SHA-256 of the JSON array containing the original `go.mod` text and `go.sum` text (an absent sum is the empty string), in that order. Existing module or manifest requires `--force`; a failed replacement restores the previous pair. Expected YAML hashes are never updated automatically. `code validate` checks an adjacent manifest when present; deployment only requires the Agent, YAML and module.

`test --build` uses the same build operation and executes only after it succeeds. A failed build never runs the previous module. A successful build remains when subsequent business execution fails. `--source`, `--offline`, and `--force` apply only to build or `test --build`.

### Test input and results

`--params JSON` and `--params-file FILE` are exclusive; omitting both supplies `{}`. Input uses the production JSON decoder, schema validator, defaults, file receiver, controller, SDK and isolated worker. Invalid input fails before business execution. Local tests perform real business effects allowed by the capability's sandbox and policies. They do not test API key authorization or REST/MCP transport.

For a file property, supply its inline object with `name`, `mime_type`, and standard strict Base64 `data`, or put `null` at that exact leaf and pass repeatable `--input-file POINTER=PATH`:

```sh
onprest-agent code test --config ./agent.yaml --capability process_document \
  --params '{"documents":[null,null]}' \
  --input-file '/documents/0=./input = one.pdf' \
  --input-file '/documents/1=./second.bin' \
  --input-mime '/documents/1=application/pdf' --format json
```

`--input-file` and `--params-file` require regular files. Their final path component cannot be a symlink or reparse point; the CLI opens without following it and validates that same handle before reading. Devices, FIFOs, sockets and directories fail before business execution.

Pointers use JSON Pointer escaping and existing array indices; missing leaves, duplicates, non-file targets, non-regular paths and a binding without a `null` placeholder fail. MIME overrides apply only to the same local file binding and use a concrete type without parameters. Extensions `txt`, `csv`, `json`, `pdf`, `png`, `jpg`/`jpeg`, `gif`, `mp4` and `zip` have fixed MIME mappings; other extensions use `application/octet-stream`. File name, MIME, extension, empty-file, byte and count constraints still apply. Local filesystem paths are accepted by this CLI adapter only.

Every operation accepts `--format text|json` (default `text`). stdout contains only the operation result. JSON always has `operation` and `ok`; build/validate success includes `module`, `sha256`, `abi`, `imports` and, when applicable, `manifest`. Successful test includes its new ULID `request_id`, projected `data`, and ordered `files` containing `name`, `mime_type`, `size_bytes`, `sha256`, and optionally `saved_path`. Failure includes a safe `error` with `code`, `message`, optional `reason`, and observed `outcome`; it excludes data/files and private diagnostic detail. A valid SDK `PublicError` preserves its safe `APP_*` code/message. Help and success exit `0`, execution/compiler/validation/output failure exits `1`, and invalid usage exits `2`.

Compiler diagnostics, SDK logs, captured Wasm stdout/stderr and internal details go to CLI stderr with control characters escaped. Redirect the two streams separately. `--log-level debug|info|warn|error` overrides YAML `logging.level` for test; omission uses YAML, then `info`. It changes recorded diagnostics only. Compiler diagnostic display is limited to 1 MiB while pipes continue draining. See [Logging](/reference/logging#agent).

### Save local output files

```sh
mkdir -p ./saved
onprest-agent code test --config ./agent.yaml --capability process_document \
  --params-file ./params.json --output-dir ./saved --format json > result.json 2> diagnostic.log
```

Without `--output-dir`, every output reader is still fully consumed and checked, and only metadata remains. With it, the CLI requires an existing directory and opens it safely before business execution. It saves all validated bytes in a private run directory, closes and flushes everything, then publishes `DIR/<request_id>/` with an atomic rename that never replaces an existing path. Filenames are ordered `0001`, `0002`, etc., with the original name's final ASCII alphanumeric extension of 1–16 characters lowercased when present. Original names remain in metadata, and `saved_path` is an absolute local path. Zero files produces no final directory. `--force` never overwrites local test output.

YAML delivery remains part of lint and definition hashing. Local test uses this local saver rather than REST/MCP rendering, so success does not establish reference retrieval, direct response count, or inline-envelope delivery limits. Common output projection, CSV generation, file count/byte/size/digest checks still apply.

Invalid output directories fail before business execution. Copy/disk/competition/finalization failure reports CLI-only `CLI_OUTPUT_FAILED`, exit `1`, and an outcome reflecting that business execution may already have occurred. The CLI never retries business execution. Normal failure and cancellation release readers, run spool and unfinished output. Cleanup failures report residual paths to stderr and exit `1`; completed output survives cleanup or stdout-write failure. Forced termination can leave run-named private `.onprest-code-*` directories; these are unfinished output and can be removed manually after that run stops. Other runs' directories are never scanned or removed.

## Validate Agent startup

```bash
./onprest-agent validate --config ./capability.yaml
./onprest-agent validate --config ./capability.yaml --format json
```

`validate` uses the same startup preparation as normal Agent startup: full YAML load and lint, then preparation of only referenced providers and sources. DB capabilities open their databases, use a Ping bounded to 10 seconds, and run driver-specific EXPLAIN with their effective policy timeout. HTTP preparation snapshots its fixed source and credentials without sending business HTTP. It exits before Gateway challenge retrieval or WebSocket connection and never executes a capability. A successful check therefore does not prove Gateway reachability or runtime behavior.

The config path priority is the same as normal startup: `--config`, `--capability-file`, `AGENT_CAPABILITY_FILE`, then `capability.yaml` beside the binary. `--format` is case-sensitive and accepts `text` (default) or `json`.

For a DB configuration, text success is one stdout line:

```text
validation succeeded: driver=postgres capabilities=2
```

For the same DB configuration, JSON success is one stdout object:

```json
{
  "valid": true,
  "database_driver": "postgres",
  "capabilities": 2
}
```

Without DB capabilities, JSON success omits `database_driver` and the text `driver=` value is empty. No database is required.

Validation failures use exit `1`. Text failures go to stderr; JSON failures go to stdout with `valid:false`, a fixed `stage`, and a safe `message`. The fixed stages are `config`, `busy`, `detail_log`, `database_open`, `database_ping`, `capability_explain`, `canceled`, and `internal`. Usage errors, including unknown flags, formats, commands, and positional arguments, use exit `2`; help and successful validation use exit `0`.

DB-specific detail is never included in CLI output. Read a validation log only when text output reports a validation detail-log path or JSON includes `detail_log`; configuration and busy failures do not create one, and diagnostic-finalization failure deliberately omits that field. See [Agent Local Logs](/agent/local-logs) for the file lifecycle and protection rules, and [Troubleshooting](/operations/troubleshooting#db-ping-or-explain-startup-failure) for operator actions.

Configuration diagnostics never reproduce unsafe YAML keys verbatim: keys outside the bounded identifier form, including keys with whitespace, quotes, line breaks, or terminal control characters, are replaced by a fixed placeholder. The lifecycle lock remains held through the completed text or JSON write. Unlock/close is attempted exactly once afterward; a native release error cannot append another record, switch output streams, or contradict the already completed validation result, and process exit remains the kernel-level release fallback.

After a crash, recovery remains bounded to strictly named validation temporary files. The lifecycle lock remains held through output completion so concurrent commands cannot report the wrong run. Detailed recovery, cleanup, and file-protection guidance is centralized in [Agent Local Logs](/agent/local-logs).

## Diagnose Agent and Gateway

```bash
./onprest-agent doctor --config ./capability.yaml
./onprest-agent doctor --config ./capability.yaml --format json
```

`doctor` runs the same configuration and referenced-provider preparation as `validate`, then checks the configured Gateway's DNS, TCP connection, TLS, challenge, and Agent-key verification. Each Gateway network stage is bounded to 10 seconds and the complete command to 60 seconds. A failed stage is reported as `failed` and dependent stages as `skipped`; `ws://` reports TLS as `skipped` with code `NOT_APPLICABLE`. The command does not replace a running Agent connection or execute a capability.

Default text writes one safe line per check to stdout:

```text
doctor config: passed (OK) configuration is valid
doctor gateway_tls: skipped (NOT_APPLICABLE) TLS is not used for ws://
```

JSON always uses this schema and preserves check order:

```json
{
  "ok": true,
  "checks": [
    {
      "stage": "config",
      "status": "passed",
      "code": "OK",
      "message": "configuration is valid"
    }
  ]
}
```

The actual result includes every preparation and Gateway stage. A successful doctor exits `0`, a completed check failure exits `1`, and invalid arguments or formats exit `2`. Output contains safe summaries only.

See [Troubleshooting](/operations/troubleshooting#run-the-doctor-probe) for stage-specific actions and [Agent Local Logs](/agent/local-logs) for protected diagnostic files.

## Agent Service Commands

```bash
./onprest-agent service install --config /absolute/path/capability.yaml
./onprest-agent service start
./onprest-agent service stop
./onprest-agent service status
./onprest-agent service uninstall
```

These are individual commands, not an apply-change sequence; there is no `service restart` command. Use the copy-paste-safe [existing-service change procedure](/operations/capability-changes#apply-a-change-to-an-existing-service) or the separate [new-service installation procedure](/operations/capability-changes#install-a-new-service).

`service remove` is an alias for `service uninstall`. The service commands register and control the agent through the host OS service manager: systemd on Linux, launchd on macOS, and Windows Service on Windows. `status` reports `service`, `native`, `installed`, and `state`, plus PID/config/binary/unit fields when available. If `install` omits `--config`, it registers `capability.yaml` next to the `onprest-agent` binary. `install` does not enable automatic start on OS boot.

## Build from Source

```bash
make build
```

Expected outputs:

```text
dist/onprest-gateway
dist/onprest-agent
```

## Cross Build

This is the source-build interface for developers. Operators can instead use a
[binary release archive](/operations/deployment#binary-release-installation),
which requires neither this repository nor a Go toolchain on the installed host.

```bash
make build-cross
```

This writes OS-specific artifacts under `dist/<os>-<arch>/`, for example:

```text
dist/linux-amd64/onprest-gateway
dist/linux-amd64/onprest-agent
dist/linux-arm64/onprest-gateway
dist/linux-arm64/onprest-agent
dist/darwin-amd64/onprest-gateway
dist/darwin-amd64/onprest-agent
dist/darwin-arm64/onprest-gateway
dist/darwin-arm64/onprest-agent
dist/windows-amd64/onprest-gateway.exe
dist/windows-amd64/onprest-agent.exe
```

The binaries are built with `CGO_ENABLED=0`, so they are suitable for copying to legacy environments without installing Docker or native database client libraries.
