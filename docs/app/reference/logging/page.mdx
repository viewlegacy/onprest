# Logging Reference

## Gateway

The gateway writes JSON Lines to stdout.

Request event fields:

| Field | Description |
|---|---|
| `protocol` | `rest` or `mcp` |
| `request_id` | Gateway-generated ULID shared with the public envelope and Agent request; separate from an MCP JSON-RPC `id` |
| `timestamp` | UTC event time in RFC 3339 format |
| `event` | Always `request` for a request event |
| `capability` | capability name when available |
| `api_key_name` | API key name from config |
| `http_status` | response status |
| `count` | DB SELECT or CSV filtered row count, or DML affected count on success; null for HTTP/file/Wasm success and every failure |
| `executor_kind` | Executor kind on successful execution; `db`, `csv`, `file`, `http`, or `wasm` |
| `returned_rows` / `affected_rows` | Measured DB SELECT or CSV filtered row count, or DML affected count on success; the other counter is null; both are null for HTTP/file/Wasm |
| `file_count` | Number of published files on success |
| `response_bytes` | Canonical published data bytes on success; `null` is four bytes |
| `input_file_count` / `input_file_bytes` | Agent-confirmed input file count and decoded file bytes; separate from output counters. On rejection/cancellation, only confirmed measurements are included; otherwise omitted. See [Gateway Logs](/gateway/logs#request-event) |
| `outcome` / `reason` | Observed outcome and optional fixed safe reason for business failures |
| `error_code` | Public application code returned to the caller, or null |
| `error_message` | Matching public response message, or null on success |
| `duration_ms` | Non-negative request duration in milliseconds |

Execution metrics remain available when output is omitted.

For REST and HTTP-level MCP errors, `error_code` and `error_message` match the HTTP `error.code` and `error.message`. For MCP JSON-RPC errors they match `error.data.code` and `error.message`; for MCP tool execution errors they match the public agent code/message, whether carried in the text result on `2025-03-26` or in `result.structuredContent.error` on the two newer versions.

Gateway stdout excludes submitted param values, URL paths, SQL, DB credentials, agent raw detail, plaintext API keys, and agent private keys. See [Gateway Logs](/gateway/logs) for the rules that determine when REST, MCP, and control events are emitted.

Control events:

| Event | Fields | Description |
|---|---|---|
| `openapi_cached` | `paths` | Emitted after Gateway caches the completed public OpenAPI document. This is always summary-only. |
| `openapi_snapshot` | `paths`, `openapi` | Emitted only when `GATEWAY_EMIT_OPENAPI_SNAPSHOT=true`. `openapi` contains the public document for all exposed capabilities, including Gateway-added `servers`, `securitySchemes`, and `security`. |
| `mcp_http_rejected` | `http_status`, `error_code`, `error_message` | Safe MCP HTTP-boundary diagnostic. It is a control event, not a request event. |

`openapi_snapshot` is not filtered per API key. The Agent excludes capabilities hidden by `expose_in_openapi: false`, but the event may contain public descriptions, input/output schemas, annotations, and examples for every exposed capability. It must not contain SQL, secrets, or DB connection information.

## Agent

Agent local detail is saved next to the `onprest-agent` binary:

```text
onprest-agent.log
```

`capability.yaml` controls the severity threshold and rotation:

```yaml
logging:
  level: info
  max_size: 10MB
  max_files: 3
```

`logging.level` accepts `debug`, `info`, `warn`, or `error` and defaults to `info`. Only records at the configured severity or higher are saved. Set `logging.level: debug` to capture SDK `Log("debug", ...)` messages.

SDK `Log` messages and captured Wasm stdout/stderr are written to this local detail log, not Agent process stdout or the result channel. Captured Wasm stdout uses `info`; stderr uses `warn`. Wasm diagnostics share a finite byte budget per execution; messages are split into bounded records, and excess output is truncated with a local warning.

`max_size` defaults to `10MB`; `max_files` defaults to `3`. Agent stdout is for process-level events. Private preparation and runtime execution detail belongs in the rotating local detail log, including DB-specific errors and HTTP failures. OS service managers may redirect agent stdout/stderr to separate process log files; those files do not replace `onprest-agent.log`.

The standalone `validate` and `doctor` commands use separate, non-rotating diagnostic files. See [Agent Local Logs](/agent/local-logs) for their lifecycle and access controls.

Author `code test` routes the same SDK/provider diagnostics to CLI stderr, including capability and request context, with control characters escaped. Its stdout contains only the operation result. `--log-level` overrides the YAML threshold for this run without changing results or definition hashes. `code build` also keeps compiler diagnostics on stderr, with a shared 1 MiB display budget and continued pipe draining. These commands use neither the rotating runtime log nor validation/doctor diagnostic files. See [Author CLI](/reference/cli#build-and-test-wasm-code).
