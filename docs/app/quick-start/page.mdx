# Quick Start

This guide starts the prebuilt gateway and agent as separate processes and verifies REST API, MCP, OpenAPI, and healthz. No source checkout, Go toolchain, or `make` is needed.

## 1. Download Binaries

Download the binary archive for your host and the Quick Start files. These links follow the latest GitHub Release:

| Host | Download |
|---|---|
| Linux x64 | [⬇ Binary archive](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-linux-amd64.tar.gz) |
| Linux ARM64 | [⬇ Binary archive](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-linux-arm64.tar.gz) |
| macOS Intel | [⬇ Binary archive](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-darwin-amd64.tar.gz) |
| macOS Apple silicon | [⬇ Binary archive](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-darwin-arm64.tar.gz) |
| Windows x64 | [⬇ Binary archive](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-windows-amd64.zip) |
| All hosts | [⬇ Quick Start files](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-quickstart.tar.gz) |

Save both files in one directory and extract them into a working directory. Replace `linux-amd64` with your host:

```bash
mkdir -p onprest/examples
cd onprest
tar -xzf ../onprest-linux-amd64.tar.gz --strip-components=1
tar -xzf ../onprest-quickstart.tar.gz --strip-components=1 -C examples
```

On Windows PowerShell:

```powershell
mkdir onprest\examples
cd onprest
tar -xf ..\onprest-windows-amd64.zip --strip-components=1
tar -xzf ..\onprest-quickstart.tar.gz --strip-components=1 -C examples
```

Run the remaining commands from this directory. It contains the two deployable units and the example files.

```text
onprest-gateway
onprest-agent
examples/
```

Docker is optional for the Onprest OSS core. This guide uses Docker only to provide a disposable local PostgreSQL database for the example capability.

## Quick Start Example Files

The Quick Start files are matching examples for local evaluation:

- `examples/gateway.env`
- `examples/capability.postgres.yaml`
- `examples/postgres.compose.yml`
- `examples/postgres-init.sql`

Those files contain a matching agent key pair and API key hash. If you use them, use the example plaintext API key in the verification steps and skip the key/config creation steps below. These credentials are public; never reuse them in a real deployment.

Start the example PostgreSQL database.

```bash
docker compose -f examples/postgres.compose.yml up -d --wait
```

This starts a local PostgreSQL container on `127.0.0.1:5432`, creates the `legacy` database, creates the `capability_user` account used by `examples/capability.postgres.yaml`, and seeds the `customers` table. The role has `SELECT` plus column-level `UPDATE (name)` on `customers`; it has no INSERT, DELETE, or DDL privilege. If `127.0.0.1:5432` is already in use, stop that PostgreSQL instance or edit both `examples/postgres.compose.yml` and `examples/capability.postgres.yaml` to use the same alternate port.

Without Docker, you can use an existing PostgreSQL instance instead: create an empty disposable `legacy` database, run `examples/postgres-init.sql` against it as an administrator, and update `database` in `examples/capability.postgres.yaml`. Do not run the SQL against a production database.

For real deployments, generate fresh keys and start from the production templates described in the archive's `INSTALL.md`. The example's `ws://localhost` URL is for loopback development only; a non-loopback deployment must use `wss://` as described in [Deployment](/operations/deployment).

## 2. Generate Agent Keys

> Steps 2–5 create your own keys and config. **If you are using the Quick Start example files, skip steps 2–5 and continue at step 6.**

The agent holds an Ed25519 private key. The gateway holds only the public key.

```bash
./onprest-gateway create-agent-secret
```

Put the generated private key in `gateway.agent_private_key` in `capability.yaml`, and put the public key in `GATEWAY_AGENT_PUBLIC_KEY` in `gateway.env`.

The shorter command alias is also available.

```bash
./onprest-gateway create-agent
```

## 3. Generate API Key

Create API keys for API users or MCP clients.

```bash
./onprest-gateway create-key --name internal --capabilities "get_customer,update_customer"
./onprest-gateway create-key --name partner-a --capabilities "get_customer,get_orders"
```

`"*"` grants all capabilities. Omitted or empty capabilities mean zero permissions.

## 4. Create `gateway.env`

`gateway.env` configures the gateway process.

```env
# Required.
GATEWAY_AGENT_PUBLIC_KEY=base64url-ed25519-public-key
GATEWAY_API_KEYS_JSON='[{"name":"internal","key_hash":"$2a$10$xxxxx","capabilities":["get_customer","update_customer"]}]'

# Optional. Omit these to use defaults or disabled behavior.
# GATEWAY_ADDR=:8080
# GATEWAY_PUBLIC_URL=http://localhost:8080
# GATEWAY_CORS_ALLOWED_ORIGINS=http://localhost:8090
# GATEWAY_IP_ALLOW_LIST=203.0.113.0/24
# GATEWAY_TRUSTED_PROXY_CIDRS=172.16.0.0/12
# GATEWAY_RATE_LIMIT_REQUESTS_PER_SECOND=10
# GATEWAY_RATE_LIMIT_BURST=20
# GATEWAY_EMIT_OPENAPI_SNAPSHOT=false
# GATEWAY_MAX_REQUEST_BODY_BYTES=1048576
```

The `key_hash` value in `GATEWAY_API_KEYS_JSON` is a bcrypt hash, so it contains `$`. Single-quote the whole JSON value when loading it through a shell.

## 5. Create `capability.yaml`

The agent treats `capability.yaml` as the only capability definition.

```yaml
service:
  title: Example CRM Capabilities
  version: 0.1.0
  description: Example agent-defined capabilities for a legacy CRM database.

runtime:
  max_concurrent_requests: 16

gateway:
  url: ws://localhost:8080/ws/agent
  agent_private_key: base64url-ed25519-private-key

database:
  driver: postgres
  host: localhost
  port: 5432
  name: legacy
  user: capability_user
  password: onprest-example-password

logging:
  max_size: 10MB
  max_files: 3

defaults:
  readonly: true
  timeout: 30s
  max_rows: 1000
  max_bytes: 1MB

capabilities:
  get_customer:
    description: Fetch one customer by id.
    sql: select id, name, email from customers where id = :customer_id
    params:
      customer_id:
        type: integer
        required: true
        minimum: 1
        description: Customer ID.
    policy:
      timeout: 3s
      max_rows: 1
      max_bytes: 256KB
      expose_in_openapi: true
    result:
      id:
        type: integer
        description: Customer ID.
      name:
        type: string
        description: Customer name.
      email:
        type: string
        description: Customer email address.
  update_customer:
    description: Update one customer's name.
    sql: update customers set name = :name where id = :customer_id
    params:
      customer_id: { type: integer, required: true }
      name: { type: string, required: true, minLength: 1, maxLength: 200 }
    policy:
      readonly: false
      timeout: 3s
      max_affected_rows: 1
      max_bytes: 256KB
```

The example API key explicitly allows only `get_customer` and `update_customer`. Mutation success is `{"count": n}`. Zero affected rows is still success; decide whether that is a business error in the caller. See [Capability YAML](/agent/capability-yaml#policy) for policy options.

## 6. Validate the Agent Configuration

Validate the exact configuration file that the Agent will start with. For the Quick Start example, run:

```bash
./onprest-agent validate --config ./examples/capability.postgres.yaml
```

If you created your own file in step 5, run this instead:

```bash
./onprest-agent validate --config ./capability.yaml
```

Validation performs YAML lint, DB Ping, and SQL EXPLAIN preparation without connecting to the Gateway or executing a capability. If it fails, do not start the Agent; follow [Troubleshooting](/operations/troubleshooting#db-ping-or-explain-startup-failure).

## 7. Start Gateway and Agent

The commands below use the Quick Start example files. If you created your own files in steps 2-5, replace `./examples/gateway.env` with `./gateway.env` and `./examples/capability.postgres.yaml` with `./capability.yaml`.

Start the gateway.

```bash
set -a
. ./examples/gateway.env
set +a
./onprest-gateway
```

Start the Agent in another terminal, passing the same configuration path that succeeded in step 6. For the Quick Start example, run:

```bash
./onprest-agent --config ./examples/capability.postgres.yaml
```

If you validated your own file, run this instead:

```bash
./onprest-agent --config ./capability.yaml
```

On Windows PowerShell, the gateway also reads its settings from process environment variables. Load the example file and start it, then start the Agent in another PowerShell window:

```powershell
Get-Content .\examples\gateway.env |
  Where-Object { $_ -match '^GATEWAY_[A-Z_]+=' } |
  ForEach-Object {
    $name, $value = $_ -split '=', 2
    Set-Item "env:$name" $value.Trim("'")
  }
.\onprest-gateway.exe
```

```powershell
.\onprest-agent.exe --config .\examples\capability.postgres.yaml
```

Use `Invoke-RestMethod` or another HTTP client for the verification requests below.

If `--config` and `AGENT_CAPABILITY_FILE` are both omitted, the agent reads `capability.yaml` next to the `onprest-agent` binary.

The agent connects outbound to `/ws/agent`. During connection, the gateway verifies the signature with the agent public key. After connection, the gateway calls the internal `meta` capability to fetch the agent-generated OpenAPI spec and caches it in memory (see [OpenAPI](/api/openapi)).

## 8. Verify Health

```bash
curl -s http://localhost:8080/healthz
```

`/healthz` can be called without an API key. It monitors the gateway process and agent connection state, while still honoring the gateway IP allow list and per-source rate limit when those controls are configured.

```json
{
  "ok": true,
  "agent_connected": true
}
```

## 9. Verify REST Read and Mutation

Set the plaintext API key in the shell that will call the gateway. If you are using the Quick Start example files, use the example plaintext key.

```bash
export ONPREST_API_KEY='orjrqqPeX8FXhsECOnrnOr6oa70pOYjyeUWmxTbaZrM'
```

```bash
curl -s \
  -X POST http://localhost:8080/api/v1/capabilities/get_customer \
  -H "Authorization: Bearer ${ONPREST_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"customer_id":1}'
```

A successful call returns the rows the capability is allowed to expose:

```json
{
  "rows": [
    { "id": 1, "name": "Ada Lovelace", "email": "ada@example.com" }
  ],
  "count": 1
}
```

The REST request body is the capability params object directly. Do not wrap it in `{"params": {...}}`.

Update that customer through REST:

```bash
curl -s \
  -X POST http://localhost:8080/api/v1/capabilities/update_customer \
  -H "Authorization: Bearer ${ONPREST_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"customer_id":1,"name":"Ada REST"}'
```

```json
{ "count": 1 }
```

## 10. Verify OpenAPI

```bash
curl -s \
  -H "Authorization: Bearer ${ONPREST_API_KEY}" \
  http://localhost:8080/openapi.json
```

OpenAPI is fetched from agent metadata, cached by the gateway, and filtered by the API key's allowed capabilities. It does not include SQL text or DB connection information.

## 11. Verify MCP

```bash
curl -s \
  -X POST http://localhost:8080/mcp \
  -H "Authorization: Bearer ${ONPREST_API_KEY}" \
  -H "Content-Type: application/json" \
  -H "MCP-Protocol-Version: 2025-11-25" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

```bash
curl -s \
  -X POST http://localhost:8080/mcp \
  -H "Authorization: Bearer ${ONPREST_API_KEY}" \
  -H "Content-Type: application/json" \
  -H "MCP-Protocol-Version: 2025-11-25" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"update_customer","arguments":{"customer_id":1,"name":"Ada MCP"}}}'
```

The tool result contains `structuredContent: {"count": 1}`. MCP `tools/list` is generated from the OpenAPI document and filtered by the API key's allowed capabilities.

## 12. Verify Committed Database State

Read through the capability boundary again:

```bash
curl -s \
  -X POST http://localhost:8080/api/v1/capabilities/get_customer \
  -H "Authorization: Bearer ${ONPREST_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"customer_id":1}'
```

The returned name is `Ada MCP`. You can also verify the disposable database directly:

```bash
docker compose -f examples/postgres.compose.yml exec -T postgres \
  psql -U onprest_admin -d legacy -Atc "SELECT name FROM customers WHERE id = 1"
```

The command prints `Ada MCP`, confirming the REST update and subsequent MCP update committed.

## 13. Stop Example Database

Stop both binaries with Ctrl+C, then remove the example database:

```bash
docker compose -f examples/postgres.compose.yml down -v
```

To build from source instead, see [CLI Reference](/reference/cli#build-from-source).
