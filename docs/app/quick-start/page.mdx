# Quick Start

Run the released gateway and agent against a disposable PostgreSQL database, then call a capability through REST and MCP. You need Docker for the example database only; no source checkout or Go toolchain.

<Steps>

### Download

Download two archives from the latest release: the binaries for your host, and [`onprest-quickstart.tar.gz`](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-quickstart.tar.gz) with the example files.

| Host | Binaries |
|---|---|
| Linux x64 | [`onprest-linux-amd64.tar.gz`](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-linux-amd64.tar.gz) |
| Linux ARM64 | [`onprest-linux-arm64.tar.gz`](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-linux-arm64.tar.gz) |
| macOS Intel | [`onprest-darwin-amd64.tar.gz`](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-darwin-amd64.tar.gz) |
| macOS Apple silicon | [`onprest-darwin-arm64.tar.gz`](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-darwin-arm64.tar.gz) |
| Windows x64 | [`onprest-windows-amd64.zip`](https://github.com/viewlegacy/onprest/releases/latest/download/onprest-windows-amd64.zip) |

Extract both into a new working directory:

<Tabs items={['macOS / Linux', 'Windows']} storageKey="os">
<Tabs.Tab>

```bash
mkdir -p onprest/examples
cd onprest
tar -xzf ../onprest-linux-amd64.tar.gz --strip-components=1   # your host's archive
tar -xzf ../onprest-quickstart.tar.gz --strip-components=1 -C examples
```

</Tabs.Tab>
<Tabs.Tab>

```powershell
mkdir onprest\examples
cd onprest
tar -xf ..\onprest-windows-amd64.zip --strip-components=1
tar -xzf ..\onprest-quickstart.tar.gz --strip-components=1 -C examples
```

</Tabs.Tab>
</Tabs>

Run every remaining command from this directory. It now holds `onprest-gateway`, `onprest-agent`, and `examples/`, which includes a matching agent key pair and an API key.

<Callout type="warning">
The example credentials are public. Use them only on your own machine.
</Callout>

### Start the example database

```bash
docker compose -f examples/postgres.compose.yml up -d --wait
```

This starts PostgreSQL on `127.0.0.1:5432` with a `customers` table in a `legacy` database. The agent connects as `capability_user`, which can only `SELECT` from `customers` and update its `name` column.

If port 5432 is taken, change it in both `examples/postgres.compose.yml` and `examples/capability.postgres.yaml`. Without Docker, create an empty `legacy` database on a PostgreSQL server you can discard, run `examples/postgres-init.sql` against it as an administrator, and adjust `sources.databases.primary` in `examples/capability.postgres.yaml`.

### Validate the agent configuration

```bash
./onprest-agent validate --config ./examples/capability.postgres.yaml
```

`validate` checks the YAML, connects to the database, and runs `EXPLAIN` on each capability's SQL. It executes nothing and does not contact the gateway. If it fails, see [Troubleshooting](/operations/troubleshooting#agent-fails-at-startup-or-validate).

### Start the gateway and the agent

<Tabs items={['macOS / Linux', 'Windows']} storageKey="os">
<Tabs.Tab>

Start the gateway with the example settings:

```bash
set -a
. ./examples/gateway.env
set +a
./onprest-gateway
```

In a second terminal, start the agent:

```bash
./onprest-agent --config ./examples/capability.postgres.yaml
```

</Tabs.Tab>
<Tabs.Tab>

The gateway reads its settings from environment variables. Load the example settings and start it:

```powershell
Get-Content .\examples\gateway.env |
  Where-Object { $_ -match '^GATEWAY_[A-Z_]+=' } |
  ForEach-Object {
    $name, $value = $_ -split '=', 2
    Set-Item "env:$name" $value.Trim("'")
  }
.\onprest-gateway.exe
```

In a second PowerShell window, start the agent:

```powershell
.\onprest-agent.exe --config .\examples\capability.postgres.yaml
```

</Tabs.Tab>
</Tabs>

The agent creates private `identity` and `spool` directories next to its configuration, so it needs write permission there.

### Call a capability

Call `get_customer` with the example API key. The request body is the capability's input object itself.

<Tabs items={['macOS / Linux', 'Windows']} storageKey="os">
<Tabs.Tab>

```bash
export ONPREST_API_KEY='orjrqqPeX8FXhsECOnrnOr6oa70pOYjyeUWmxTbaZrM'

curl -s \
  -X POST http://localhost:8080/api/v1/capabilities/get_customer \
  -H "Authorization: Bearer ${ONPREST_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"customer_id":1}'
```

</Tabs.Tab>
<Tabs.Tab>

```powershell
$env:ONPREST_API_KEY = 'orjrqqPeX8FXhsECOnrnOr6oa70pOYjyeUWmxTbaZrM'

Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/v1/capabilities/get_customer `
  -Headers @{ Authorization = "Bearer $env:ONPREST_API_KEY" } `
  -ContentType 'application/json' -Body '{"customer_id":1}' | ConvertTo-Json -Depth 10
```

The remaining steps use `curl`. On Windows, send the same requests with `Invoke-RestMethod` as above.

### Change data through REST and MCP

`update_customer` changes a customer's name. Call it through REST:

```bash
curl -s \
  -X POST http://localhost:8080/api/v1/capabilities/update_customer \
  -H "Authorization: Bearer ${ONPREST_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"customer_id":1,"name":"Ada REST"}'
```

```json
{
  "request_id": "01J5ABCDEF1234567890ABCDEF02",
  "result": { "data": { "count": 1 }, "files": [] }
}
```

Then call the same capability as an MCP tool:

```bash
curl -s \
  -X POST http://localhost:8080/mcp \
  -H "Authorization: Bearer ${ONPREST_API_KEY}" \
  -H "Content-Type: application/json" \
  -H "MCP-Protocol-Version: 2025-11-25" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"update_customer","arguments":{"customer_id":1,"name":"Ada MCP"}}}'
```

The tool result carries the same envelope in `structuredContent`. Call `get_customer` again and the name is now `Ada MCP`. You can also check the database directly:

```bash
docker compose -f examples/postgres.compose.yml exec -T postgres \
  psql -U onprest_admin -d legacy -Atc "SELECT name FROM customers WHERE id = 1"
```

### Look at the published contract

```bash
curl -s -H "Authorization: Bearer ${ONPREST_API_KEY}" http://localhost:8080/openapi.json
```

The OpenAPI document and the MCP `tools/list` result are generated from the agent's capability definitions and filtered to what the API key may call. They contain input and output schemas, never SQL or connection details.

### Clean up

Stop both binaries with Ctrl+C, then remove the example database:

```bash
docker compose -f examples/postgres.compose.yml down -v
```

</Steps>

## What you just ran

`examples/capability.postgres.yaml` defines the database source `primary` and two capabilities that use it:

```yaml
capabilities:
  get_customer:
    description: Fetch one customer by ID.
    executor:
      type: db
      source: primary
      sql: select id, name, email from customers where id = :customer_id
    input:
      properties:
        customer_id: {type: integer, minimum: 1}
      required: [customer_id]
    policy: {max_rows: 1}
    output:
      data: {}
      items:
        properties:
          id: {type: integer}
          name: {type: string}
          email: {type: string}

  update_customer:
    description: Update one customer's name.
    executor:
      type: db
      source: primary
      sql: update customers set name = :name where id = :customer_id
    input:
      properties:
        customer_id: {type: integer, minimum: 1}
        name: {type: string, minLength: 1, maxLength: 200}
      required: [customer_id, name]
    policy: {readonly: false, max_affected_rows: 1}
    output: {data: {}}
```

- `executor` is the SQL that runs. Callers can only supply `:customer_id` and `:name`.
- `input` is the JSON Schema each call is validated against before anything runs.
- `policy` sets limits. `readonly: false` is what allows the `UPDATE`.
- `output` declares what is returned: only `id`, `name`, and `email`, whatever else the table holds.

The example API key in `examples/gateway.env` may call only these two capabilities. [Capabilities](/capabilities) explains each section, and [Databases](/capabilities/databases) covers the DB executor.

## Try without a database

The same two binaries run every other executor. Each example has its own configuration and a README with the commands:

| Executor | Example | What it shows |
|---|---|---|
| CSV | [examples/csv](https://github.com/viewlegacy/onprest/tree/main/examples/csv) | Filter a CSV from a folder or an upload, and download the selected rows as a new CSV |
| File | [examples/file-output](https://github.com/viewlegacy/onprest/tree/main/examples/file-output) | Download a completed report from a folder |
| File | [examples/file-input](https://github.com/viewlegacy/onprest/tree/main/examples/file-input) | Upload a PDF and save it into a folder |
| HTTP | [examples/http](https://github.com/viewlegacy/onprest/tree/main/examples/http) | Call an internal API with validated arguments and publish part of its response |
| Code | [examples/sdk](https://github.com/viewlegacy/onprest/tree/main/examples/sdk) | Build a Go module with the SDK, test it locally, and call it through the gateway |
